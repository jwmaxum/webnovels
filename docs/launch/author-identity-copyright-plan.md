# 작가 가입·권리 확약·PASS 계획

기준일 2026-10-21. 34단계의 구현·인수 계약이다. [구현 기록](stage34-author-enrollment.md)에
가입 화면·서버·DB 절차가 있으며, 사용자는 미계약 상태로 연동 준비를 선택했다.
**실제 PASS 서비스를 개시하거나 아래 초안의 법률 검토가 완료된 것은 아니다.**
[Author/Creator 계약](author-creator-contract.md)을 유지한다.

## 가입 흐름과 동의 문안 초안

이메일을 인증한 사용자가 작가 가입을 선택하면 아래 확약과 개인정보 안내를 읽고, 필수
동의를 직접 선택한 뒤 PASS 본인확인을 진행한다. 서버 확인 후 필명을 등록하고 Author를
생성한다. 동의를 거절하거나 인증에 실패하면 작성한 입력을 보존하고 재시도 경로를 제공한다.

> 본인은 게재하는 작품을 직접 창작하였으며 해당 작품의 저작권이 본인에게 귀속됨을
> 확약합니다. 타인의 창작물을 도용하거나 제3자의 권리를 침해하지 않았음을 확인합니다.
> 본인의 도용 또는 권리 침해로 발생하는 민사·형사 등 법적 책임은 관련 법령에 따라
> 본인이 부담하며, 권리 확인 요청과 분쟁 해결 절차에 협조합니다.

위 문안은 법률 검토용 초안이다. 계약만으로 형사책임을 정하거나 플랫폼 자신의 법정 책임까지
이전한다는 문구를 넣지 않는다. 공동 창작·원작 각색·정당한 이용허락 작품에는 기여자/원작자와
권리 근거를 구분하여 확인하는 별도 경로를 설계한다. 이를 본인의 단독 저작물이라고 허위
확약하도록 만들지 않는다. 원작자 저작권과 플랫폼의 한정된 게시·유통 허락을 구분한다.

권리 확약, 본인확인에 필요한 개인정보 안내/동의, 선택 마케팅 동의를 분리한다. 확약은
가입 시 한 번 기록하고 작품 최초 발행의 `rightsConfirmed`에도 정확한 작품·권리 문서 버전을
연결한다. 변경된 문서에 과거 동의를 소급 기록하지 않는다. [저작권법 제10조](https://www.law.go.kr/법령/저작권법/제10조)는 문구 검토의 기준 자료다.

## 한 본인의 여러 계정

| 개념 | 관계·권한 |
|---|---|
| 검증된 본인 | 제공자 계약상 허용된 안정 식별자로 내부 person ID 생성. 실명·전화번호 단독 일치로 병합하지 않음 |
| Auth 사용자 | 각각의 로그인 ID. 현 이메일 로그인에서는 별도 확인 이메일 사용. 같은 본인의 여러 Auth UUID 허용 |
| Author 프로필 | Auth UUID당 기존 작가 프로필 1개. 동일 person ID가 여러 Author와 연결될 수 있음 |
| 필명 | 계정별 별도 선택. 기존 필명 충돌 규칙 유지; 실명과 같을 필요 없음 |
| 작품 소유권 | `actor.author.id`만 사용. person ID 공유가 다른 계정 작품의 읽기·편집·정산 권한을 주지 않음 |

본인 확인이 같다는 이유만으로 신규 가입을 거절하거나 필명을 강제 통일하지 않는다. A 계정의
인증 완료 거래를 B 계정에 재사용하지 않고 B도 자기 세션에서 새 인증을 완료한다. 같은 본인에
대한 person upsert는 원자적으로 처리하되 account 매핑에 `unique(person_id)`를 두지 않는다.
동명이인·개명·휴대전화 번호 변경·명의 변경을 구분하고, 실명/연결된 다른 필명 목록은 공개하지 않는다.
다른 계정의 제재 처리나 회피 판단은 근거·이의신청·권한을 갖춘 별도 정책으로 다룬다.

## 서버 설계와 데이터 최소화

기존 `server/providers/portone-identity.mjs`는 서버 조회와 Auth UUID/거래 ID/채널/모드/시각
확인을 이미 수행하지만 **생년월일 검증용**이다. 작가 실명·본인 식별자 검증까지 완료됐다고
간주하지 않는다. 제공자 계약 후 작가 가입 목적의 어댑터를 추가하고 공통 검증을 재사용한다.
조회/응답 규격은 [PortOne V2 본인인증 API](https://developers.portone.io/api/rest-v2/identityVerification),
클라이언트 연동은 [V2 본인인증 요청](https://developers.portone.io/sdk/ko/v2-sdk/identity-verification-request?v=v2)을 기준으로 고정한다.

- `author_identity_attempts`: 서버 생성 난수 거래 ID, Auth UUID, 가입 목적, 예상 상점/채널/모드,
  만료 시각과 PENDING/VERIFIED/FAILED/EXPIRED 상태. 같은 세션에 묶고 소비 완료 거래 재사용 금지.
- `verified_author_persons`: 내부 UUID와 제공자 범위의 CI/DI 등 허용된 식별자에 대한 keyed HMAC,
  키 버전. 제공 항목/안정성/이용 목적이 확인된 후 한 종류를 선택한다. 원문을 일반 DB/로그에
  저장하지 않는다. HMAC도 개인정보로 보호하며 무작위 salt로 같은 본인을 매번 다르게 만들지 않는다.
- `author_identity_accounts`: Auth UUID/Author ID와 person ID 연결, 검증 거래 ID·확인 시각.
  Auth UUID는 유일하고 person ID에는 여러 행을 허용한다. 서버 트랜잭션에서 프로필과 함께 확정한다.
- `author_rights_consents`: Auth UUID, 문서 버전/해시, 동의 시각, 가입/작품 목적, 필요한 작품 ID.
  불변 감사 기록과 열람/정정/삭제 요청 절차를 분리한다.

주민등록번호·통신사 비밀번호를 수집하거나 저장하지 않는다. 실명은 제공자 확인에 필요하지만
영구 저장 여부는 별도 목적과 보존기간을 정한 뒤 결정한다. 실명 보관이 필요한 경우 암호화하고
권한 있는 담당자만 조회하며 접근 로그를 남긴다. CI/DI, 전화번호, 응답 원문, 비밀키는
브라우저·분석 이벤트·에러 메시지·Git에 남기지 않는다. 개인정보 항목·보존/파기·처리위탁/제3자
제공 구분은 실제 제공자 계약과 [개인정보 보호법 제16조](https://www.law.go.kr/법령/개인정보보호법/제16조)를 기준으로 검토한다.

클라이언트의 성공 URL/쿼리, 입력한 실명, PASS 팝업 완료만으로 VERIFIED를 저장하지 않는다.
서버가 해당 거래를 재조회하고 상점·채널·LIVE 모드·시각·소유 세션을 모두 확인한다. 결제 성공이나
기존 성인 플래그는 이 절차를 대체하지 않는다. 콜백 처리, 응답 유실, 프로필 생성 재시도는
멱등 처리하고 한 트랜잭션으로 인증 소비·동의 확인·Author 연결을 확정한다.

## 구현 순서·인수

1. 제공자/계약·PASS 사용 채널·실명/식별자 제공 범위·요금·약관/개인정보 문구·보존기간 확정.
2. 비공개 schema·명시적 ACL/RLS·1:N 매핑·동의 문서 버전과 등록 RPC 작성. 브라우저 직접 쓰기 금지.
3. 기존 onboarding/작가 가입 UI에 동의→인증→필명 입력과 재시도 연결. 별도 `/author` API를 만들지 않음.
4. TEST 환경에서 동의 누락/위조, 만료, 타인 거래, 타 채널, LIVE/TEST 혼동, 중복 콜백,
   네트워크 유실/동시 가입, A/B 복수 계정 성공과 상호 작품 접근 거절을 검증.
5. 기존 작가 전환 안내·유예/재인증 조건과 고객지원 절차 확정. 원고 읽기·저장·백업/ID 연결 보존.
6. 실제 제공자 LIVE 검증과 허용된 기기 인수 후 제한 적용. 실패 시 가입 전환만 닫고 기존 원고 보존.

사용자 요청은 복수 계정 허용이다. 임의의 1인 1계정 제한이나 계정 자동 병합은 완료 조건에
포함하지 않는다. PASS 계약과 법률 검토가 준비되지 않으면 코드·TEST 인수와 LIVE 개시 상태를
구분하여 보고한다. 다음 운영 단계는 무료 신규 연재의 hosted/Storage/Images/Cron 인수다.
