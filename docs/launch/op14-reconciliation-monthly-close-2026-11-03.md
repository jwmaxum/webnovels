# OP-14 — 입금 예외 대사·재증빙·월마감·운영 준비

## 구현 결과

기존 관리자 ‘작가 정산’의 실제 금융 영역에 **입금 예외·월마감·운영 준비**를 추가했다. 새 상위 메뉴는 만들지 않는다. 실제 송금은 관리자가 은행에서 별도 처리하고 완료 증빙을 기록하는 기존 방식이다. OP-13의 금융 기능 비활성 상태를 유지한다.

- 미확정 입금/환불·취소를 거래·주문·회원 ID로 검색하고 금액 불일치, 증빙 만료, 입금 안내 변경, 보류, 재증빙 대기로 필터링한다.
- 원거래에 보류 사유의 문서/문의 참조를 기록하고 다른 관리자가 해제한다. 보류 또는 재증빙 검토 중에는 입금·정정 확정을 막는다. 정정 반려는 가능하다. 해제는 충전·환불 완료를 뜻하지 않는다.
- 재증빙은 같은 은행 계좌 내부 식별자와 거래번호의 HMAC에 일치해야 한다. 기존 금액·발생일·주문·수혜자는 바꾸지 않는다. 원본은 덮어쓰지 않고 새 증빙과 독립 승인 이력을 연결한다. 만료·파기된 원본은 되살리지 않는다.
- 월 내역 조회 → 초안 작성 → 다른 관리자 승인 → 고정 JSON 내려받기를 제공한다. 한국 시간 월 경계와 장부 기록일로 집계하며 은행 발생일은 별도 필드다. 현재 월은 조회만 가능하다. 마감 후 달라진 과거 내역은 이전 마감을 연결한 수정본으로 남긴다.
- 정산 암호화 키의 새 쓰기 버전과 구 버전 읽기를 지원한다. 거래 중복 판정·멱등 요청의 HMAC는 기존 v1 키에 고정한다. 실제 운영 키를 바꾸거나 기존 암호문을 일괄 재암호화하지 않았다.
- 운영 준비 화면은 활성 표시 관리자 수, 미결 검토, 정산 개인정보·증빙의 키 버전 사용량과 읽기 키 누락, SMTP/복원/실거래 근거의 입력 여부를 보여준다. 입력 여부를 인수 성공으로 표시하지 않는다.

## 원장·권한 계약

`027_commerce_operations.sql`은 026이 있는 DB와 `webnovels.commerce_operations_apply_verified=true`를 요구하고 재실행을 거절한다. 비공개 테이블 6개는 RLS를 활성화하며 `public/anon/authenticated/service_role` 직접 접근을 금지한다. 기존 OP-13 금융 잠금을 공유하고 서비스 전용 `op14_commerce_operations`만 호출한다. 현재 Auth·최고 관리자 권한 검증은 멱등 결과 조회보다 먼저 수행한다.

027에는 정적 `CREATE OR REPLACE`로 OP-13 RPC의 호환 정의를 포함했다. 바뀐 거래 동작은 입금/정정 확정의 **미결 검토 차단과 현재 승인 증빙 확인**이다. 기존 공개 콘텐츠 함수와 권한은 교체하지 않는다. 공통 증빙 envelope 검증은 키 버전 `v1`~`v999`를 수용하도록 확장하되 실제 서버 keyring에 없는 키는 암복호화할 수 없다.

보류 해제자는 등록자·수혜자와 달라야 한다. 재증빙 승인자는 제출자·원거래 기록자·수혜자와 달라야 한다. 새 증빙 승인 후에도 원거래의 독립 입금/정정 확인이 별도로 필요하다. 보류 등록·해제·증빙 제출/검토·월마감은 append-only다. 거래 UUID 요청 키와 암호문 IV를 제외한 입력 지문을 유지하여 응답 유실 재시도를 처리한다.

서버 API는 기존 `/api/v2/admin/live-commerce`를 확장한다. 엄격한 Zod 입력, POST 동일 origin, 220KB 요청 제한, 민감 작업의 비밀번호 재확인, 현재 권한 검증을 사용한다. proof-context 조회는 서버 내부에서만 사용하며 은행 HMAC를 UI에 반환하지 않는다. 원문 증빙·계좌 식별자·은행 참조는 목록/내보내기에 넣지 않는다. 증빙과 다운로드 URL은 화면/계정 전환 및 60초 만료 때 제거한다.

## 마감 자료의 의미

입금 기록, 확정 포인트 충전, 회차 구매/작가 발생 수익, 환불/은행 입금 취소, 작가 수익 취소, 정산 신청/취소/송금 완료를 분리한다. 충전액을 바로 작가 수익으로 계산하지 않는다. 합계는 PostgreSQL의 정수/정밀 합산과 문자열 응답을 사용하여 JavaScript 정밀도 손실을 피한다.

마감에는 원천 이벤트 ID·회차·가격 정책·계약 참조·lot 배분과 당시 미결 검토 목록을 저장하고 SHA-256 지문을 고정한다. 해당 월의 보류·재증빙 검토가 남아 있으면 승인할 수 없다. 승인 시 현재 내역과 지문을 재비교하고, 이전 승인 ID를 고정하여 동시 승인으로 수정 이력이 갈라지지 않게 한다. 이전 JSON 파일은 이후 정정으로 바뀌지 않는다. 트랜잭션 시작 시각과 실제 기록 시각이 월 경계를 넘는 경우도 원천 membership과 새 수정본으로 구별한다.

한 월은 10,000 이벤트·약 3MB 이벤트 JSON 한도로 제한한다. 초과하면 일부를 누락한 성공 파일을 만들지 않고 명시적으로 거절한다. 내보내기는 세무 검토 자료이며 법정 신고서가 아니다. OP-13 정산 신청의 `sources`는 누적 적격 구매 참조다. **각 지급에 독점 배분된 원천 금액 명세가 아니므로** 이를 중복 합산하면 안 된다. 지급별 독점 원천 배분과 신고 형식은 OP-15에서 확장한다.

## 키 회전과 SMTP 준비

기존 `AUTHOR_SETTLEMENT_ENCRYPTION_KEY`는 v1 키로 계속 유지한다. 새 선택적 비공개 설정 `AUTHOR_SETTLEMENT_ENCRYPTION_KEYS_JSON`은 `{ "v1": "기존 키", "v2": "새 키" }` 형태이며 최대 16개 키를 받는다. 실제 값은 문서·Git·채팅에 넣지 않는다. `AUTHOR_SETTLEMENT_KEY_VERSION=v2`를 선택하면 새 쓰기는 v2, 읽기는 envelope의 키 버전으로 수행한다. keyring의 v1이 기존 키와 다르거나 선택한 버전이 없으면 차단한다.

은행 참조 중복 판정과 기존 멱등 지문은 v1 키·v1 domain으로 고정했다. AES 쓰기 키를 바꿔도 같은 은행 거래의 HMAC가 달라지지 않는다. 구 암호문, 백업, 중복 판정 때문에 v1 키를 임의 삭제할 수 없다. 유출 키의 완전 폐기나 기존 암호문의 일괄 교체 도구를 구현했다고 주장하지 않는다. 별도 복원·키 인벤토리·백업·정책 검토 후 운영 설정을 전환해야 한다. 파기된 증빙 원문과 만료일을 복원/연장하지 않는다.

기존 SMTP 설정 도구는 `https://webnovels.uk`가 이미 사이트 URL이면 이를 보존한다. 선택적 `BETA_AUTH_SITE_URL`은 이 도메인과 기존 Pages 도메인만 허용하고 wildcard 리디렉션을 추가하지 않는다. 설정 검사와 `deliveryVerified=false`를 구분한다. 실제 SMTP 설정 변경·메일 발송·금융 알림 발송은 수행하지 않았다. Auth SMTP를 금융 알림 발송 기능으로 간주하지 않는다.

## 현재 운영 준비 상태

2026-11-03 읽기 전용 확인 결과:

- OP-13 최종 Cloudflare 배포 성공. 두 도메인의 파일 및 API 비활성 상태 확인 완료.
- 별도 hosted 복원 대상: 미설정. 운영 DB로 복원 시험하지 않았다.
- 실제 입금 안내·금융 증빙 보관 정책: 미설정.
- SMTP: 로컬 입력과 Supabase 설정 모두 없음. 현재 Auth 사이트 URL은 Pages 도메인이다.
- 암호화: 기존 v1 설정만 존재. 키 전환·증빙 파기 워커 설정/배포를 수행하지 않았다.
- 사용자는 ‘아직 없음 — 기능 개발·검증 계속’으로 답변했다. 운영 DB/플래그·키·Auth 설정 변경, 실제 증빙 업로드·입금·송금·메일 발송은 수행하지 않는다.

`npm run inspect:op14`는 설정과 복원 대상 메타데이터를 읽기 전용으로 점검한다. 비밀 원문 없이 `scratch/op14/readiness.json`에 결과를 기록한다. `LIVE_COMMERCE_HOSTED_RESTORE_REF`와 `LIVE_COMMERCE_BANK_ACCEPTANCE_REF`는 준비 근거의 참조만 표시하며 실인수의 자동 인증 기능이 아니다.

## 조사·검증

search-first 연구 에이전트와 제한된 저장소 검색으로 기존 Zod·WebCrypto·pg/PGlite·정산 암호화·재인증·SMTP 도구를 재사용했다. 새 의존성을 추가하지 않았다. Codebase Memory는 주 에이전트에서 연결 종료, 연구 에이전트에서는 일치하는 인덱스 부재로 소스 탐색을 사용했다. npm/PyPI 새 패키지 비교나 실제 은행/PG 호출은 하지 않았다.

시간대·월 경계는 [PostgreSQL 날짜/시간](https://www.postgresql.org/docs/17/functions-datetime.html), 잠금과 snapshot은 [트랜잭션 격리](https://www.postgresql.org/docs/17/transaction-iso.html), 암호화는 [WebCrypto AES-GCM](https://www.w3.org/TR/2017/REC-WebCryptoAPI-20170126/#aes-gcm), 메일 설정과 발송 검증 구분은 [Supabase SMTP](https://supabase.com/docs/guides/auth/auth-smtp)를 참고했다.

검증 결과는 `artifacts/op14-verification-2026-11-03.json`에 기록한다. 합성 DB·가상 DOM·네이티브 PostgreSQL 복원은 실거래·hosted 복원·실기기 인수를 대신하지 않는다. localhost HTTP/브라우저 검증은 수행하지 않는다.

## 다음 OP-15 — 운영 전환 전 예외 처리 완결

1. 승인된 정책·회사 수취 계좌·독립 관리자·별도 복원 대상·SMTP를 준비한다. 025~027의 별도 hosted 복원과 권한·키 읽기·파기 워커를 인수한 뒤 제한 실거래를 진행한다.
2. 오연결 입금 재연결, 부분/초과 입금의 반환·합산을 별도 불변 원장과 독립 승인으로 구현한다. OP-14의 보류 해제를 금액 정정이나 충전으로 사용하지 않는다.
3. 정산 지급별 독점 원천 배분과 마감 후 환불 회수/차감, 개인·사업자·법인별 세무 자료 형식을 확정한다. 대량 월마감은 분할 내보내기로 확장한다.
4. 금융 알림 outbox·중복 방지·재시도 및 실제 SMTP 발송 인수를 구현한다. 암호문 재암호화·중단 복구·키 폐기와 은행 참조 HMAC 키 교체는 별도 보안 전환 절차로 구현한다.
5. 준비된 환경에서 10,000원 입금→100P 열람→환불/작가 수익→관리자 외부 송금 완료를 소액으로 대조한다. Toss 카드·자동 지급은 계약·실제 키가 준비된 후 선택적으로 연동한다.
