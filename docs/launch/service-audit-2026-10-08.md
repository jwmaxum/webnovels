# 웹소설 웹툰 서비스 점검과 개선 방향

기준일: 2026-10-08 KST. 소스 기준: `090fe02` 및 당시 변경 없는 작업 트리. 실행 계획은 [후속 개발 로드맵](development-roadmap-2026-10-08.md), 바로 다음 작업은 [14단계](../../improve14.md)를 따른다.

작가의 비공개 작품 등록과 원고 보존, 서버 소유권 검사, 관리자 운영 조회는 재사용할 기반이 갖춰져 있다. 가장 먼저 해결할 일은 전체 콘텐츠 공개 전환과 첫 연재의 완성이다. 웹툰은 이미지 뷰어만으로 완성되지 않으며, 작가 업로드부터 보호된 공개본과 독자 열람까지 별도로 연결해야 한다.

서비스 방향은 **쉽게 연재하고, 편하게 이어 읽으며, 신인 작품도 발견할 수 있는 웹소설·웹툰 플랫폼**으로 제안한다. 초기에는 신인 장르소설과 소수의 검증된 웹툰에 집중하고, 실제 이용과 연재 지속률을 확인한 뒤 수익화와 규모를 확장한다.

## 1 점검 근거와 현재 상태

| 근거 | 확인한 범위 | 해석 |
|---|---|---|
| 현재 소스 | `public/`, `server/`, `functions/`, 증분 SQL, 테스트·CI 구성 | 구현과 호출 구조 확인. 화면 배치와 실제 기기 사용성은 별도 인수 필요 |
| 운영 적용 기록 | 2026-09-25~26 계정·작가 작업실·대시보드·관리자·큐레이션 기록 | 해당 시점의 실제 적용 근거. 2026-10-08 운영 상태의 새 확인으로 취급하지 않음 |
| 기존 출시 문서 | `improve.md`, 관련 4~13단계·계약·출시 게이트 | 전체 콘텐츠 공개 판정은 NO GO. 일부 제한 기능의 운영 적용과 구분 |
| 경쟁 서비스 | 문피아 공식 FAQ·랭킹, 레진 공식 홈·요일별 목록·작품 상세 | 공개 동선과 정보 구성 비교. 비공개 작가 도구·내부 운영은 확인 범위 밖 |
| 이번 검증 | 기존 출시 회귀 구성 및 TypeScript 검사 | 최종 결과는 아래 검증 기록에 기재 |

운영 주소의 콘텐츠 health·계정 health·카탈로그에 읽기 요청을 시도했으나 이 환경에서 HTTP 응답을 확보하지 못했다. 따라서 오늘의 응답을 200 또는 503으로 단정하지 않는다. 마지막 저장소 기록에서는 콘텐츠 서비스가 `503 SECURE_API_NOT_ACTIVATED`이고 계정·비공개 작가 작업실·일부 관리자 기능은 별도 준비 검사로 제공된다. [복구 기록](503-recovery-plan.md), [작가 작업실](author-workspace-rollout.md), [관리자 적용 기록](admin-console-rollout.md).

2026-09-26 기록의 Auth 연결 41건은 가상 작가 30·가상 독자 10·확인된 최고 관리자 1의 연결이다. 실제 고객 확보·사용성 검증·베타 참여자 수로 사용하지 않는다. 보류 본문 78건도 그 시점의 기록이며, 웹툰 이미지 회차를 포함하므로 빈 텍스트만 보고 누락·삭제·자동 재분류하지 않는다.

`improve.md`와 일부 이슈 표에는 Auth 연결 0건, 관리 API 401 등 이전 상태가 남아 있다. 실제 후속 적용 기록과 대조해 항목별로 최신 근거를 붙여야 한다. 1~13단계를 모두 미구현 또는 모두 완료로 판정하는 것은 부정확하다.

전체 재작성보다 기존 계약을 유지하면서 빠진 연결과 사용 흐름을 보완하는 편이 적합하다. Cloudflare 업무 구현은 `server/`와 `functions/`가 기준이며, 과거 Express/SQLite의 `src/`·Prisma 구현을 현재 운영 서비스로 혼동하지 않는다.

두 서비스의 기능을 모두 한 번에 복제하기보다 **원고 보존, 정확한 이어보기, 신인 발견, 예측 가능한 비용과 정산**에 집중한다. 이것이 소규모 서비스가 우선 검증할 차별화 가설이다.

## 5 작가 등록과 연재의 대안

### 공통 작품 등록

현재 제목만으로 비공개 작품을 만드는 방식은 유지한다. 첫 단계에 웹소설·웹툰 유형을 추가하되 소개·표지·홍보 문구를 모두 채워야 저장할 수 있게 만들지 않는다. 제목과 유형으로 시작한 후 작품 화면에서 작성 재개와 공개 준비 상태를 보여준다.

추천 흐름은 `유형·제목 선택 → 비공개 생성 → 첫 회차 작성/가져오기 → 작품 정보 확인 → 독자 화면 미리보기 → 즉시/예약 공개 → 독자 화면 보기·다음 회차`다. 단계마다 입력과 저장 상태를 유지하고, 공개에 필요한 정보만 마지막 확인에서 요구한다.

장르는 주 장르 선택과 제한된 부 장르, 태그는 검색·추천이 있는 선택 UI로 제공한다. 내부 canonical 코드와 표시 명칭을 분리해 ‘현대 판타지/현대판타지’ 같은 차이를 정리한다. 공개 등급·권리 확인·AI 사용 표기·댓글 정책은 명확히 안내하고 기본값을 동의로 오인하지 않는다.

계정 인증, 작품 권리 확인, 계약·정산 검증은 별개 상태로 관리한다. 비공개 작성의 낮은 진입장벽과 공개 콘텐츠의 책임을 함께 설계하며, 본인확인 방식과 시점은 운영 정책으로 확정한다. 이름·필명·기본 ID로 소유자를 추정하지 않는다.

### 웹소설 작성

- 웹 편집, TXT/DOCX 가져오기를 같은 초안 저장·revision 경로로 연결한다. 기존 원고의 자동저장·변경 전 백업·충돌 복구를 유지한다.
- 다중 파일 가져오기는 제목·순서·글자 수·누락 경고·저장 상태를 행별로 보여준다. 공개 전 충분히 검토하며 일괄 가져오기 자체가 일괄 발행이 되지 않게 한다.
- 표지·소개·등급 등 미입력 항목에 해당 설정으로 가는 버튼을 제공한다. 사용 불가능한 기능은 왜 준비 중인지와 가능한 다음 작업을 표시한다.
- HWP/HWPX·한 파일 회차 분리·AI 보조는 실제 작가 수요 이후 확장한다. 원본 보존·분리 미리보기·명시적 수락을 먼저 설계한다.

### 웹툰 작성

웹툰도 동일한 Author 신원·소유 작품·초안 UUID·revision·불변 공개본을 사용한다. 기존 `/creator`와 `/api/v2/creator/*` 계약을 확장하며 별도 작가 계정 체계를 만들지 않는다.

1. 회차 제목·썸네일·글/그림/원작 크레딧을 입력하고 여러 이미지 파일을 선택한다. 파일명 숫자 정렬은 제안이며 작가가 최종 순서를 확인한다.
2. 썸네일 목록에서 순서 이동·삭제·재시도·파일별 진행 상태를 제공한다. 서버 업로드 결과와 회차 revision을 확인한 후 저장 완료를 표시한다.
3. 업로드 완료 파일의 manifest에 객체 ID·순서·크기·해상도·해시·처리 상태를 기록한다. 원본은 private로 보존하고 서버 검증·재인코딩을 통과한 파생본만 사용한다.
4. 긴 이미지의 분할·축소·WebP 등 파생 처리를 원본과 별도로 관리한다. 같은 업로드 재시도는 중복 객체/패널을 만들지 않고 미완료 파일 정리는 초안 참조·보관 정책을 확인한다.
5. 미리보기와 독자 뷰어가 같은 manifest를 사용한다. 공개·예약은 이미지 처리가 끝난 특정 revision을 고정하고 이전 공개본과 원본을 보존한다.
6. 서버가 작품 공개 상태·등급·열람 권리를 검증한 뒤 이미지 접근을 허용한다. 제한 콘텐츠의 CDN 캐시·서명 만료·공개 철회까지 확인하고 긴 회차의 만료 갱신도 마련한다.

최초 제안 업로드 형식은 JPEG/PNG이며 폭·총 픽셀·파일당/회차당 용량·패널 수 제한은 실제 원고 샘플과 모바일 메모리 시험으로 확정한다. 기존 소설 파일의 2 MiB 제한을 그대로 웹툰에 적용하지 않는다. 외부 URL 쉼표 입력과 임의 URL 가져오기는 신규 등록 방식에서 제외한다. 파일 서명·형식·용량·저장 분리와 재인코딩 기준은 [OWASP 파일 업로드 지침](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)을 참고한다.

## 6 독자 UI의 대안

| 홈 | 유형 전환, 이어보기, 오늘 업데이트, 편집 추천, 신인 발견 | 처음 온 독자는 읽을 작품을 찾고 기존 독자는 바로 이어 읽음 |

| 작품 상세 | 첫 화/이어보기, 관심·작가 구독, 소개·태그·일정·크레딧, 회차 정렬·읽음 상태 | 첫 회차가 1번이 아니어도 실제 첫 공개 회차로 이동 |
| 소설 뷰어 | 본문 중심, 글꼴·테마, 회차 목록, 본문 위치 복원, 다음 공개 회차 | 댓글 길이와 관계없이 읽기 위치·완독이 정확함 |

| 내 서재 | 읽는 중·관심작·업데이트·완독/보관, 작가 구독, 알림 설정 | 다른 기기와 계정 전환에서 기록·노출이 정확함 |
| 장애·빈 상태 | 최초 이용·검색 0건·권한 제한·네트워크 오류·서비스 준비를 구분 | 실패를 빈 작품 목록이나 성공으로 안내하지 않음 |

모바일 하단 5개 메뉴는 `홈·탐색·랭킹·서재·내 정보`를 기본안으로 삼고, 탐색에서 소설/웹툰을 전환한다. 데스크톱은 같은 정보 구조를 사용한다. 작가 스튜디오와 관리자 진입은 계정 메뉴에 둔다. 독서 중에는 본문 외 탐색 요소를 줄이고 회차 목록·설정·다음 화를 쉽게 찾게 한다.

추천은 초기에는 편집·장르·최근 업데이트·신인 노출 규칙으로 시작한다. 이후 검증된 독서 이벤트로 개인화하며, 취향 제외·추천 이유·설정 초기화를 제공한다. 독자가 제외한 태그나 성인 등급은 홈·랭킹·이벤트에도 같은 정책을 적용한다.

클릭 카드와 아이콘 버튼은 링크/버튼 의미·이름·키보드 포커스를 갖춰야 한다. 자동 슬라이드의 정지와 동작 감소 설정, 대비·확대·스크린리더 상태 안내를 포함해 [WCAG 2.2](https://www.w3.org/TR/WCAG22/) 기준으로 인수한다. 이 문서는 현재 화면의 WCAG 적합성을 판정하지 않는다.

## 7 관리자 메뉴의 타당성과 정리

현재 11개 메뉴의 업무 범위는 대체로 타당하다. 메뉴 수를 줄이는 것보다 실제 처리 권한과 업무 완료 동선을 정리하는 것이 우선이다. 정산 메뉴 복구는 후속 사용자 요청으로 추가된 조회 전용 범위이므로 예전 제거 계획만 보고 다시 삭제하지 않는다.

| 현재 메뉴 | 권장 위치 | 유지·개선 기준 |
|---|---|---|
| 운영 대시보드 | 운영 현황 | 공개/비공개·실제/시험 데이터를 구분, 예약·파일 처리 실패·지원 대기·장애 표시 |
| 작품 CMS·회차 CMS | 콘텐츠 관리의 작품/회차 탭 | 검색·메타데이터·노출 제한·큐레이션. 작가 대행 작성·본문 수정·임의 소유자 변경 없음 |
| 신고·콘텐츠 검수·이의제기 | 사건 처리의 종류별 탭 | 사건 연결, 담당·우선순위·기한·증거·사유·통지. 이의제기 접수를 자동 제재 해제로 취급하지 않음 |
| 작가·독자 관리 | 계정 지원 | 역할별 서버 권한 유지, 복구·정지·이력·연결 확인. 이메일/필명만으로 계정 병합하지 않음 |
| 가상 계정 관리 | 최고 관리자 개발·시험 도구 | production 업무 지표에서 제외, 명확한 시험 표시, 일반 운영 메뉴의 핵심 위치에서 분리 |
| 작가 정산 | 수익·정산 | 지금은 이전 기록 조회·검증 상태. 실제 원장과 지급 연결 후 재무 업무 확장 |
| 서브관리자·권한 | 권한 관리 | 최소 권한·재인증·즉시 회수·감사, 기존 권한 이름과 영속 계약 보존 |
| 감사·처리 기록 | 감사 기록 | 계정·권한·큐레이션·신고·정산 기록을 사건/대상 기준으로 추적 |
| 서비스 운영 설정 | 서비스 설정 | 기능의 준비/활성 상태·버전·담당·선행 조건. 설정 체크박스만으로 출시 승인하지 않음 |

큐레이션에는 노출 위치·기간·순서·시작/종료·미리보기·변경 이력을 추가한다. ‘편집 추천’ 설정과 실제 인기 랭킹을 분리한다. 콘텐츠 제한과 공개 철회는 목록·검색·캐시·본문·이미지에서 일관되게 반영한다.

광고·팬미팅·굿즈·대형 이벤트는 담당·정산·재고·취소·지원 체계가 준비될 때 독립 확장한다. 계좌번호 원문·비공개 초안은 일반 운영 조회에서 제외하고 필요한 예외 접근은 사유·최소 권한·감사 기록을 요구한다.

## 8 사업 모델과 출시 범위

권장 출시 순서는 무료 웹소설 검증 → 무료 웹툰 검증 → 단일 수익모델 검증이다. 소설과 웹툰 동시 오픈이 필요하면 두 유형의 모든 출시 조건을 충족한 뒤 한 번에 판정한다. 무료 공개와 성인·결제·광고·후원 활성화는 각각 별도 범위다.

수익모델은 무료 샘플과 명확한 유료 이용권을 기본 후보로, 선택형 보상 광고를 다른 후보로 검증한다. 광고를 모든 회차의 필수 관문으로 만들기 전에 이탈률과 실제 순매출을 측정한다. 첫 수익화에서는 후보 하나만 선택하고 정책·검증된 업체 이벤트·원장·취소·작가 배분·정산을 완성한다.

작가 화면에는 예상·확정·지급 가능·지급 완료를 실제 근거에 따라 구분한다. 이전 수익·시드 원장을 합산하지 않는다. 계좌 암호화 키의 보존·회전·재암호화와 송금 증빙도 지급 인수에 포함한다. [현재 계좌 계약](author-dashboard-rollout.md), [수익화 계약](monetization-contract.md).

저작권·독점/비독점·수익 배분·연재 중단·신고·탈퇴·구매권 보존·환불·개인정보에 관한 정책은 제공 범위에 맞춰 확정한다. 원본과 독자 권리를 보존하는 처리 규칙을 먼저 마련하고, 필요한 외부 검토와 운영 담당을 연결한다.

## 9 개선 효과의 측정

‘최고의 대안’은 첫 연재 성공, 안정적인 독서, 작가·독자 재방문으로 검증한다. 아래는 제안 지표이며 현재 측정 성과가 아니다. 가상 계정·시드 작품·운영자 자신의 열람은 고객 지표에서 제외한다.

| 목표 | 측정 정의 | 초기 사용 방식 |
|---|---|---|
| 첫 연재 성공 | 신규 작가의 작품 생성 → 첫 회차 공개 → 다른 독자 열람 비율·소요 시간 | 이탈 단계별 원인 조사, 원고 준비 시간과 UI 작업 시간 분리 |
| 연재 지속 | 첫 공개 작가 중 7/28일에 추가 회차를 공개한 비율 | 소설/웹툰·신인/기존 작가를 나누어 분석 |
| 읽기 연결 | 1화 본문 열람자 중 실제 다음 공개 회차를 열람한 비율 | 단순 클릭·중복 OPEN 제외, 미완결 작품의 다음 화 유무 구분 |
| 독자 재방문 | 최초 열람 독자의 D7/D28 재열람 비율 | 표본 수·기간·익명/인증 측정 범위를 함께 표시 |
| 신인 발견 | 신인 노출 → 상세 → 본문 → 관심 등록 전환 | 조회수 조작·편집 편향 점검, 적은 표본은 순위 과장 금지 |
| 안정성 | 저장 실패·충돌 미해결·예약 지연·이미지 실패·지원 해결 시간 | 원고 전문·계좌·토큰을 이벤트에 수집하지 않음 |
| 성능 | 유형·화면·기기별 LCP·INP·CLS의 p75 | 목표 LCP ≤2.5초, INP ≤200ms, CLS ≤0.1. 실제 이용 표본과 실험실 결과 구분 |

성능 목표는 [Google Core Web Vitals](https://web.dev/articles/vitals)를 따른다. 지표의 목표값·베타 모집 규모·수익 가설은 제품 담당자가 실제 표본과 제작 비용을 보고 보정한다. 지금 임의의 전환율을 출시 성공으로 약속하지 않는다.

## 10 이번 검증 기록

- 소스·계약·운영 적용 기록의 정적 점검을 수행했다.
- TypeScript `--noEmit`: 통과. 프로젝트 설치된 컴파일러를 번들 Node로 실행했다.
- 기존 `test:release` 회귀: 15개 검증 묶음 통과. Node 테스트 러너 43개 실행의 합계 218개 통과, 실패 0·건너뜀 0. 데이터 계약 검사와 Cloudflare Functions 3개 번들 검사도 통과했다.
- 이 환경에는 `npm` 실행 파일이 없어 `npm test` 자체는 실행되지 않았다. `package.json`의 `test:release`에 등록된 각 명령을 같은 순서로 프로젝트 의존성과 번들 Node에서 직접 실행했다. 패키지 스크립트는 변경하지 않았다. [검증 요약](../../artifacts/service-audit-20261008-verification.json).
- 운영 health·카탈로그 읽기: 응답 확보 실패. 실제 운영 가동 여부 재확인 필요.
- 실제 DB/Storage 감사·SQL 적용·배포·플래그 변경·거래·계정 변경: 이번 작업에서 수행하지 않음.
- localhost·브라우저·PC/모바일 시각 인수: [프로젝트 규칙](../../.agents/rules/testing_rules.md)에 따라 미실행. UI 평가는 코드의 동선·정보·상태 처리 기준이다.
