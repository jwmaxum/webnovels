# OP-15 입금 배분·지급별 원천·금융 알림 준비

작성일: 2026-11-04. OP-14 다음 단계이며 `improve37.md`, Author/Creator 호환 계약과 기존 금융 TEST/LIVE 분리 계약을 유지한다.

## 구현한 운영 흐름

관리자의 기존 금융 영역에 **입금 배분·반환·알림 준비**를 추가했다. 최상위 메뉴는 늘리지 않는다. 실제 입금 기록과 주문을 목록에서 대조하고, 선택한 입금마다 배분액을 입력한다. 신규 메뉴와 API도 기존 LIVE 수동 금융 게이트 안에 있으므로 현재 공개 사이트에서 금융 기능이 활성화되는 것은 아니다.

| 상황 | 처리 | 금전·권리 효과 |
|---|---|---|
| 6,000원 + 4,000원 입금 | 원입금 두 건을 선택해 10,000원 충전 배분 요청 → 다른 관리자 승인 | 한 주문에 한 번만 10,000P 발급 |
| 12,000원 입금 | 10,000원 충전 배분, 잔여 2,000원 별도 보관 | 남은 금액을 자동 포인트로 바꾸지 않음 |
| 주문 오연결 | 새 주문 ID, 원천 입금, 근거 참조, 재연결 확인 → 독립 대조 | 기존 입금의 주문·은행 참조·금액은 변경하지 않음 |
| 미완납·초과 입금 반환 | 원주문에 반환 예약 요청 → 독립 승인 → 별도 실제 송금 → 제3 관리자 증빙 기록 | 충전하지 않은 잔액만 반환; 포인트 잔액에는 영향 없음 |
| 잘못된 배분 요청 | 독립 검토자가 반려 | 예약 금액 해제, 원래 요청·반려 이력 보존 |

하나의 요청은 최대 20개 입금을 선택한다. CREDIT 합계는 정확히 10,000원이다. RETURN은 같은 원주문 입금만 사용하며, 승인한 반환은 외부 송금 여부가 불명확할 수 있어 단순 취소 버튼을 제공하지 않는다. 아직 10,000원이 되지 않은 부분 입금은 미배분 상태로 남긴다. 금액을 모아 주문을 충전하려면 관리자가 명시적으로 배분한다.

배분 요청과 동시에 원천 금액을 예약하여 기존 단일 입금 확정 경로에서도 같은 입금을 재사용할 수 없다. 다른 주문 재연결은 원래 회원·새 회원·원거래 기록자와 독립된 관리자의 확인이 필요하다. 변경된 입금 안내·현재 수혜자 상태·보류·증빙 만료를 승인 시 다시 검사한다. 은행 원문의 소유자 일치는 실제 은행 자료를 보는 관리자의 대조 사항이며 API가 은행 계좌 실명을 자동 인증하지 않는다.

## 지급별 수익 배분과 취소 수익 회수

신규 정산 신청에 구매 건별 원천 금액을 FIFO 배분한다. 같은 구매 수익을 여러 미취소 지급에 중복 예약할 수 없다. 신청 취소는 기존 취소 원장을 이용해 예약을 해제하고, 원천 행을 삭제하지 않는다. 송금 완료된 배분은 계속 소비된 상태다.

이미 지급한 구매 수익이 은행 입금 취소로 취소되면 다음 신청의 새 수익을 이전 지급 회수분과 신규 지급분으로 나눈다. 예: 70원 지급 후 취소 → 새 수익 210원 발생 → 이전 지급 회수 70원 + 새 지급 140원. 회수에 사용한 구매가 다시 취소된 경우에도 미회수액을 다시 계산한다. 지급 승인·완료 시 예약 원천이 취소되었으면, 총 잔액이 양수로 돌아왔더라도 기존 신청을 차단한다. 미송금 신청을 취소하고 새 원천으로 재신청한다.

OP-13의 `payout.sources`는 누적 참고 목록이다. 이를 독점 배분으로 소급 추정하지 않는다. **028 이전의 미취소 지급에 독점 배분이 없다면 해당 지급의 승인·완료와 해당 작가의 새 신청을 보류**한다. 원래 계정·구매·지급·승인·완료 행은 그대로 보존한다. 운영 전환 시 과거 지급이 존재하면 다음 단계의 별도 검토된 소급 대사 절차가 필요하다. 미송금 신청은 현재 취소 절차로 해제 후 재신청할 수 있다.

월마감의 신규 충전에는 원천 입금별 금액, 신규 정산 신청에는 독점 원천과 회수 배분, 반환에는 원주문·원천 입금·발생 시각을 포함한다. 미결 배분과 승인 후 미완료 반환이 있는 월은 마감 승인을 막는다. 이미 승인한 JSON과 지문은 수정하지 않는다. 기존 10,000 이벤트·약 3MB 한도를 유지하고, 초과 시 누락한 파일을 만들지 않고 거절한다. 세무 신고서나 법정 보관 정책을 임의 확정하지 않는다.

## 알림 준비 범위

포인트 충전·환불/입금 취소 확정·작가 지급 완료·미충전 금액 반환과 **같은 DB 트랜잭션**에서 비공개 outbox를 만든다. 이벤트 유형+원장 ID로 중복을 막고, 사용자 UUID·이벤트 종류·원장 ID·시각만 보관한다. 계좌·이메일·증빙·비밀번호는 넣지 않는다.

관리자는 명시적으로 재시도/준비 완료 TEST를 기록할 수 있다. 최대 5회, 예상 시도 번호 검사, 멱등 요청 키로 중복·오래된 요청을 거절한다. `TEST_READY`는 외부 전송 성공이 아니며 `deliveryEnabled=false`가 고정이다. **실제 SMTP 발송 워커·lease·전송 ACK는 이번 구현에 포함하지 않는다.** 설정이 없는 상태에서 자동 attempts 증가·SENT 기록·메일 호출도 하지 않는다. 다음 단계에서 제공자별 멱등/조회 계약과 전송 후 응답 유실을 처리해야 한다.

## 데이터·보안·호환

`028_commerce_allocations.sql`은 027 존재와 `webnovels.commerce_allocations_apply_verified=true`를 요구하며 재적용을 거절한다. 새 private 테이블 8개는 같은 마이그레이션에서 RLS·직접 접근 금지·불변 트리거를 정의한다. 서비스 역할도 직접 읽기/쓰기가 안 되며 `public.op15_commerce_allocations`만 호출한다. 공통 금융 advisory lock, 현재 Auth/최고 관리자 확인, 재인증, 요청 지문, 호출 제한을 유지한다.

기존 `lots.deposit_id`는 nullable로 확장한다. 기존 단일 입금의 FK·UNIQUE는 유지하고, 합산 lot의 ID는 승인한 배분 ID와 일치하도록 트리거로 검사한다. 가상의 은행 입금이나 TEST 잔액을 만들지 않는다. 은행 참조의 HMAC 중복 검사는 입금·정정·작가 지급·미충전 반환 전체에 적용한다. 원래 공개 콘텐츠 함수·인증/Creator URL은 바꾸지 않는다.

028에 정적인 OP-13/14 RPC 호환 정의를 포함한다. 신규 트리거 거절을 한정된 오류로 반환하고, 완전히 배분한 입금을 일반 미확정 목록에서 제외한다. 미배분 금액은 기존 목록에도 표시한다. 합산·반환 및 증빙 파기 후에도 원천 ID와 금액은 보존된다.

서버는 엄격한 Zod 입력/출력, 동일 origin POST, 220KB 본문 제한과 관리자 비밀번호 재확인을 유지한다. 브라우저는 safe DOM을 사용하고 계정 전환 시 자료를 비운다. 입금 안내 hash를 클라이언트에서 주입할 수 없으며 서버 설정으로 계산한다. 반환 증빙도 기존 암호화·처리 정책·파기 계약을 사용한다.

## 조사와 검증 구분

`search-first`의 연구 에이전트로 기존 원장·정산 저널과 공식 문서를 조사했다. Codebase Memory는 현재 일치 인덱스가 없어 소스 탐색으로 대체했다. 기존 Zod/WebCrypto/pg/PGlite를 확장했으며 새 패키지를 추가하지 않았다. npm/PyPI 새 패키지 비교나 실제 은행/메일 호출을 했다고 주장하지 않는다.

참고: [Stripe 은행이체의 부분·초과 입금](https://docs.stripe.com/payments/bank-transfers/accept-a-payment?payment-ui=direct-api), [PostgreSQL 제약](https://www.postgresql.org/docs/17/ddl-constraints.html), [PostgreSQL 충돌 처리](https://www.postgresql.org/docs/17/sql-insert.html), [Supabase Queues](https://supabase.com/docs/guides/queues/pgmq). Stripe 도입이나 은행별 지원을 의미하지 않는다. 신규 큐 확장 설치보다 기존 트랜잭션 원장을 재사용하는 범위로 결정했다.

최종 검증 결과는 `artifacts/op15-verification-2026-11-04.json`에 기록한다. 합성 DB·가상 DOM·임시 네이티브 PostgreSQL 복원은 운영 DB·실제 제공자·브라우저·실거래 인수를 대신하지 않는다. localhost HTTP/브라우저는 실행하지 않는다.

## 다음 OP-16

1. 과거 지급이 있는 작가의 검토된 원천 소급 대사·불일치 해소 도구를 만들고, 대량 월마감·원천 명세의 분할 내보내기를 준비한다. 임의 소급 확정이나 기존 지급 삭제는 하지 않는다.
2. 승인 후 반환 보류·잘못된 실제 송금·합산 입금 중 일부 은행 거래 취소는 별도의 재대사/보상 분개로 확장한다. 현재 입금 취소는 lot 전체 단위이므로 원입금 일부 취소를 전체 취소로 자동 처리하지 않는다.
3. SMTP/제공자 준비 후 알림 전용 비공개 설정, batch lease·stale ACK 거절, 장애/응답 유실 재대사, 제한된 실제 발송 인수를 구현한다. Auth SMTP 준비와 금융 알림 전송을 구분한다.
4. 암호문 재암호화·중단 복구·백업 키 인벤토리·폐기 도구와 HMAC 키 교체를 별도 보안 전환으로 진행한다. 현재 v1 읽기/HMAC 키를 삭제하지 않는다.
5. 사용자에게 이미 요청한 회사 입금 안내·금융 보관/국외 처리 정책·독립 관리자·별도 hosted 복원 대상·SMTP를 준비한다. 025~028을 독립 환경에 복원하고 승인 계좌·증빙 파기 워커·소액 실거래를 인수한 뒤 LIVE 전환을 결정한다. Toss 자동 지급·카드는 계약과 TEST 키 준비 후 선택적으로 연결한다.

이번 단계는 운영 DB·기능 플래그·키·SMTP·scheduler·실제 입금/송금을 변경하지 않는다. 현재 자료 미준비라는 사용자 결정을 유지한다.
