# OP-05 충전상품·입금 대조·카드 승인/환불 TEST 구현

2026-11-02 (Asia/Seoul). TEST 코드·전체 릴리스·컴파일·타입·합성 리허설 검증을 완료했으며 운영 019·020 SQL과 금융 플래그는 적용하지 않는다. [공유 계약](op05-topups-contract-2026-11-02.md), [운영 CMS 계획](admin-cms-minimal-ux-plan-2026-11-01.md)을 따른다. 기존 무료 서비스·실제 잔액·작가/작품·원고·공개본·열람권을 보존한다.

## 화면과 업무

기존 관리자 6개 메뉴를 유지한다. 최고 관리자만 `결제·정산`의 다음 세 탭을 사용하며, 작가 정산 조회 권한을 금융 변경 권한으로 확대하지 않는다.

| 탭 | 구현 내용 |
| --- | --- |
| 결제·입금 | 충전상품 생성·불변 버전·활성/판매 기간·주문 기한, revision 충돌 방지, 주문 목록과 상세, 실제 은행 거래 참조·금액·시각·확인 사유의 수동 대조 |
| 환불·포인트 | 원충전의 미사용분 조회·전체 잔여분 환불 예약, 카드 취소/재조회·같은 환불 재시도, BANK 환불 이체 증빙 대조 |
| 대사 | REVIEW·UNKNOWN·REFUND_UNKNOWN·환불 대기 등 상태 필터, 주문별 독자 Auth UUID 확인, 서버 결과 재조회 |

독자는 별도 `/charging-test`에서 판매 중 TEST 상품과 본인 주문을 50개씩 조회한다. **상품 선택 → 가격·지급 P 확인 → 방식 선택 → 명시적 주문 생성**을 거치며 조회만으로 주문하지 않는다. `/reading-test`의 TEST 충전 링크를 통해 이동한다. 공개 홈의 메뉴를 추가하지 않는다.

기본 LOCAL_SIMULATED에서는 외부 카드 SDK를 로드하지 않고 브라우저에서 승인 영수증을 만들지 않는다. 명시적으로 주입한 서버 테스트 전송이 없으면 카드 승인/환불은 `PROVIDER_NOT_READY`다. BANK 입금 신고나 환불 버튼만으로 적립·지급 완료를 만들지 않는다.

PROVIDER_TEST에서는 검토된 TEST 설정이 있을 때 사용자 클릭으로만 공식 Toss v2 SDK를 읽는다. checkout POST가 본인 주문과 판매자 설정 binding을 동결한 뒤 공개 client key·고정 금액·customerKey·복귀 주소를 전달한다. 복귀 URL은 즉시 history에서 제거하고 본인 주문·금액과 대조한 다음 별도 서버 승인 버튼으로 확인한다. 복귀 경로의 no-referrer/no-store와 동일 Origin JSON 검증을 적용했다. 카드번호·계좌 비밀번호를 수집하지 않는다.

공개 응답의 `providerMode`는 현재 서버가 선택한 TEST 전송 경로 표시다. 실제 주문의 제공자 binding·MID·영수증은 비공개 서버 transport로 별도 검증하며 이 표시를 결제 증거로 사용하지 않는다. 브라우저/실제 SDK·업체 TEST 인수는 이번 합성 검증과 구분한다.

## 금액·포인트·환불

- 상품의 KRW와 지급 P를 분리한다. 주문 시 제목·상품 버전·금액·P·기한을 고정하고 이후 상품 변경으로 옛 주문을 바꾸지 않는다. 가입 무료 1~2화와 이후 기본 100P 정책은 OP-04를 유지한다.
- 입금 거래 참조는 전체 주문에서 한 번만 사용한다. 정확한 금액·주문 이후/기한 이내 입금 증빙만 한 번 적립한다. 부족·초과·지연 입금은 REVIEW로 보존하며 자동 정정하지 않는다. 신규 주문은 사용자별 잠금 아래 분당 60건으로 제한한다.
- 현재 OP-04 잔액은 원장 해시·건수가 있는 환불 불가 시작 lot로 보존한다. 시험 지급은 TEST_GIFT, 검증된 새 충전은 TOPUP이다. UUID·같은 생성 시각으로 과거 소비 순서를 추정하지 않는다.
- 이후 소비는 지갑 잠금과 사용자별 순번의 FIFO lot 배분이다. 각 lot의 원금 소비 누계는 `ceil(원금 × 누적 소비 P / 발행 P)`다. 1P=1원을 가정하지 않으며, 소량 소비 후 원금 전액을 환불받는 반올림 우회를 막는다.
- 환불 대상은 **원충전 한 건의 현재 미사용 P 전부**다. 일부 소비 후 남은 전부도 가능하며 임의 소량 분할 요청은 받지 않는다. 환불액은 원금에서 배정 소비액·기환불액을 뺀 값이며 0원 환불은 거절한다. 이는 TEST 계산 정책이며 실제 약관·법적 기준은 LIVE 전 확정한다.
- 총 잔액 = 사용 가능액 + 환불 예약액이다. 외부 취소 전에 잔여 P를 예약하고 기존 OP-04 구매 RPC도 예약액을 사용할 수 없게 보호한다. 다른 lot는 계속 소비할 수 있다.
- 불명 응답·시간 만료·DONE 조회만으로 환불 예약을 풀지 않는다. 확인된 취소나 BANK 환불 이체 증빙으로만 포인트 회수·REFUND 원장·환불 확정·예약 해제를 같은 거래에서 처리한다. 사용한 회차의 권리는 유지한다.
- 확정된 승인/환불의 사실은 뒤늦은 조회 실패로 지우지 않는다. 완료 환불 뒤 늦은 비확정 응답은 REFUNDED를 보존한다. 서로 모순되는 확정 영수증은 감사/검토 대상으로 보존한다.

카드 승인·조회·취소는 고정된 공식 API 주소, TEST 키·MID·주문·KRW·정확한 금액·고유 거래키를 대조한다. 15초 제한·64KiB 응답 제한·리다이렉트 거절을 사용한다. operation UUID 기반 멱등키를 유지하고 설정 binding 변경·15일 이후 변이 재전송은 차단한다. 현재 원주문별 단일 서비스 취소만 지원하며 예상 밖 외부 취소 이력은 REVIEW다. 자동 웹훅과 은행 송금 실행은 열지 않는다.

## 준비와 보안 경계

새 `020_topups_test.sql`은 검토 gate가 있는 **미적용 준비 SQL**이다. 원본 019 파일·기존 RPC 본문과 소유자·원장·공유 스키마 ACL을 보존한다. 기존 public OP-04 RPC를 같은 signature의 wrapper로 확장하고, 보존된 private base의 service 직접 실행을 회수한다. 새 비공개 테이블은 명시 ACL/RLS, 서비스 RPC는 고정 search_path와 현재 사용자/최고 관리자 재검증을 사용한다.

별도 TEST 환경에서 다음 조건이 모두 맞아야 새 API가 열린다. 이번 작업에서 운영 값을 바꾸지 않는다.

1. OP-04의 `POINTS_TEST_ENABLED=true`, `POINTS_TEST_ENVIRONMENT=TEST`, `POINTS_TEST_PROVENANCE=LOCAL_SIMULATED`, `P0_API_ENABLED=true`, FREE_BETA 비활성 조건
2. `CHARGING_TEST_ENABLED=true`
3. `CHARGING_TEST_PROVIDER`는 생략/LOCAL_SIMULATED 또는 PROVIDER_TEST만 허용. LIVE·미지정 문자열은 거절

PROVIDER_TEST는 기존 관리자 외부 연동의 암호화된 TOSS TEST 설정과 검토/활성 revision을 재사용한다. 환경 방식에서는 TEST client/secret key·merchant ID·명시 binding 버전이 필요하다. 비밀키는 공개 설정·DB 주문·응답·로그·Git에 넣지 않는다. 공개 설정에는 유효 `chargingTestEnabled` boolean만 추가한다. 설정 저장과 실제 결제 개방은 별개다.

기존 stage20의 KRW 카드 직접 구매나 구형 포인트 원장을 새 충전 원장과 합치지 않는다. Author/Creator·원고 revision·공개 head·PASS·정산 개인정보 계약도 유지한다. localStorage에 잔액·키·처리 결과를 저장하지 않으며, 미확인 요청은 계정별 메모리에 원래 내용/ID만 유지한다. 계정 변경·로그아웃·이동 뒤 늦은 응답은 폐기한다.

## 검증과 인수

신규 89개(DB 24, API/provider 18, UI VM 34, 통합 13), 전체 릴리스 55개 명령·컴파일·독립 타입 검사와 5개 흐름 합성 리허설을 통과했다. 실패·생략은 0이다. 최종 개수·종료 코드·소스 해시·Git/배포 결과는 [검증 집계](../../artifacts/op05-verification-2026-11-02.json)에 기록한다. 전체 릴리스에는 `test:op05`를 추가한다. 빌드·타입·구문·보안·diff 검토 결과를 구분하고, 설정되지 않은 린트나 VM 미계측 수치 커버리지를 통과로 꾸미지 않는다.

기존 fetch·PGlite·Node test·VM과 암호화 설정을 재사용해 새 의존성은 없다. 저장소/관련 패키지와 공식 [Toss API](https://docs.tosspayments.com/reference), [인증](https://docs.tosspayments.com/reference/using-api/authorization), [API 키](https://docs.tosspayments.com/reference/using-api/api-keys), [SDK](https://docs.tosspayments.com/sdk/v2/js/payment), [웹훅](https://docs.tosspayments.com/reference/using-api/webhook-events)을 조사했다. 새 패키지가 필요하지 않아 npm 레지스트리·GitHub 패키지 검색은 수행하지 않았다. 그래프 연결 실패로 관련 소스와 계약을 직접 검색했으며 그래프 인덱스 검증을 완료한 것으로 보고하지 않는다.

실제 PostgreSQL 다중 연결, 실제 업체 TEST·3DS/실패/취소·브라우저/휴대폰, 운영 SQL·플래그 변경, 실제 입금·카드 결제·환불·작가 지급은 실행하지 않는다. 합성 성공을 실제 금융 서비스 개방으로 표시하지 않는다.
