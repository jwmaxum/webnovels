# 운영·복구 실행 절차 — 초안

2026-09-24 현재 로컬 계약 검증만 마쳤다. 아래 절차의 운영 알림 연결, 복원 시간 측정과 실제 훈련은 미실행이다. 실제 적용 순서는 [마이그레이션·백업 절차](migration-runbook.md)를 우선한다.

## 공통 진단과 기록

1. API 응답의 `X-Request-ID` 또는 JSON `requestId`, 발생 시각, 기능, 상태 코드와 안전한 오류 코드만 사건 기록에 남긴다.
2. 인증 토큰, 서비스 키, 원고/댓글 전문, 파일 내용, 이메일·필명 등 개인 식별값은 채팅·이슈·공용 로그에 복사하지 않는다. 운영 로그의 접근 대상·보관 기간·삭제 주기는 배포 전 운영자가 확정한다.
3. 고객이 계속 작성 중이면 화면의 미동기 원고와 로컬 복구본을 먼저 보존하게 안내한다. 원고를 비우거나 다시 게시하도록 지시하지 않는다.
4. 범위와 영향(가입, 저장, 게시, 예약, 조회)을 확인하고 쓰기 차단이 필요한 경우 담당자가 알린다. 데이터가 불일치하면 기능 플래그를 임의로 켜거나 RLS를 풀지 않는다.

## 장애별 대응

| 증상 | 초동 확인 | 복구 기준 |
|---|---|---|
| 가입/로그인·메일 실패 | Auth 제공자·메일 전송 상태, `requestId`, 가입 RPC 결과, 중복 프로필 여부 | 같은 Auth UUID로 재개, 중복/권한 상승 없음. 메일 설정 변경은 별도 승인·시험. |
| 원고 저장 실패 | 로컬 복구본/서버 revision, 마지막 성공 응답, 충돌·용량·네트워크 상태 | 사본 둘 다 보존하고 명시적 충돌 해결. 실패를 저장 성공으로 표시하지 않음. |
| 파일 변환/업로드 실패 | 업로드 키, 바이트 해시, 파일 크기, Storage 확인 응답 | 확인된 성공분은 유지하고 실패분만 같은 키로 재시도. 원본 파일 보존. |
| 게시 응답 유실·중복 우려 | 멱등키, publication head, 공개 회차·스냅샷 ID | 기존 확정 결과 재조회. 새 번호로 맹목 재게시 금지. |
| 예약 지연·중단 | Cron 실행 상태, due/claimed/failed job, 제재·휴지통 상태 | 중복 실행과 공개 상태를 대조하고 같은 job을 재처리. 시간대·지연을 공지. |
| DB/Auth/Cloudflare 장애 | 실제 서비스 상태, 503 코드, 마지막 성공 시각, 배포 버전 | 읽기/쓰기 안전 상태를 확인하고 서비스 복구 후 건수·해시·권한을 대조. |

## DB + Storage 복원 훈련

1. 쓰기 제한 기준 시각을 정하고 DB와 실제 Storage 객체 바이트를 같은 기준으로 백업한다. 버킷·경로·크기·해시를 비공개 매니페스트에 기록한다.
2. 외부 메일·결제·Cron이 꺼진 **격리 환경**에 복원한다. 운영 DB/Storage를 훈련 대상으로 초기화하지 않는다.
3. 계정 연결, 작품/회차/원고 버전/공개본/예약·신고 건수와 원고 해시, FK/RLS, Storage 객체 해시 및 서명 URL 접근을 대조한다.
4. 복원 소요 시간·누락·재시도·담당자와 성공/실패 증거를 남긴다. 차이가 있으면 전환 중단 후 원본을 보존하고 원인을 조사한다.

## 알림·지원 준비 상태

저장 실패율, 가입 실패율, 파일 실패율, API 5xx, 예약 지연/실패의 운영 임계치·수신자·온콜·로그 보관은 **미설정**이다. 원고 내용 없이 요청 ID, 기능, 상태, 소요 시간, 시각만 계측해야 한다. 가입/게시 전환과 이어쓰기 시간 지표도 미구현이며, 실제 지표 파이프라인과 개인정보 검토 후 연결한다. 장애 공지 문안·문의 채널·응답 담당자와 모의 훈련 결과는 출시 전에 기록한다.

## 19단계 복구 패키지·출시 증거 연결 — 2026-10-09

[19단계 계약](stage19-quality-contract.md)과 [복구 manifest 예시](recovery-bundle.example.json)를 따른다. 기존 백업 스크립트/과거 archive는 보존한다. PostgreSQL 백업에 Storage 객체 바이트가 포함됐다고 가정하지 않는다.

1. snapshot UUID/기준 시각·쓰기 제한·담당을 정하고 전체 DB archive와 Storage 원본/파생/미참조 객체를 독립 저장장소에 보관한다. 파일 해시와 원고/권리/계정/감사 기준선을 비공개로 남긴다.
2. 격리 복원 후 schema·RPC·ACL/RLS·모든 테이블/계정 연결·bucket/객체 참조를 별도로 추출한다. 백업 state를 복원 결과로 복사하지 않는다. pg_restore --list와 실제 restore/RPC/Auth/Storage 권한·서명 URL 인수를 별도 수행한다.
3. 두 디렉터리를 npm run verify:recovery -- <백업> <복원>으로 비교한다. 도구는 실제 파일 크기/해시·DB fingerprint·참조/전체 객체 목록을 검사하며 pg_restore나 hosted 인수는 실행하지 않는다. SYNTHETIC과 실제 HOSTED_BACKUP을 구분하고 항상 hostedRestoreAccepted:false를 유지한다.
4. 소요 시간과 RPO/RTO, 독립 보관·복원 담당, 운영 알림의 실제 수신/지원 시간/공지·중단/복구를 기록한다. 오류면 기능 전환을 중단하고 원본·초안·확정 게시를 보존한다.
5. 같은 후보/환경/출시 범위의 실제 증거를 check:beta에 제출하고 담당자가 검토한다. READY_FOR_HUMAN_APPROVAL만으로 GO나 플래그 변경을 실행하지 않는다.

19단계 로컬 전체 PGlite data-directory 복원과 package 바이트 검증은 통과했으나 실제 Supabase+Storage/Auth/외부 설정 복원·알림 수신·장애 훈련·독립 보관 확인은 미실행이다.
