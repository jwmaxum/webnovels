# OP-07 작가 수익·정산 신청·지급 증빙 TEST 구현

2026-11-02 (Asia/Seoul). [공유 계약](op07-payouts-contract-2026-11-02.md), [최소 관리자 CMS 계획](admin-cms-minimal-ux-plan-2026-11-01.md), [OP-05 충전 원장](op05-topups-implementation-2026-11-02.md), [OP-06 광고 보상](op06-ad-rewards-implementation-2026-11-02.md)을 확장한다.

## 작가와 관리자 화면

작가는 기존 수익 내역에서 확정 수익, 정책 공제와 이후 감액, 지급 확인액, 신청·지급 대기액, 원거래 보류액, 신청 가능액과 부족액을 확인한다. 신청 시 현재 정책·TEST 지급 대상 버전을 함께 보낸다. 내 신청의 상세와 처리 상태를 조회하고 발송 전 신청을 취소할 수 있다. 이전 수익 기록은 별도 버튼으로 조회하며 새 지급 가능액에 합산하지 않는다.

관리자는 기존 **결제·정산 → 작가 정산**에서 정산 신청, 소비 수익 확정, 확정 명세·감액, 작가·지급 대상, 정산 정책을 처리한다. 최상위 6개 메뉴는 유지한다. 작가 필명 검색과 상태 필터, 50건 페이지, 작가 선택 후 수익·신청 바로가기를 제공해 원시 UUID를 입력하지 않아도 된다. 기존 R13 정산 서류 확인과 과거 기록 조회는 같은 메뉴의 별도 영역으로 보존한다.

승인 이후 `TEST 지급 결과 확인 시작`을 누르면 UNKNOWN 상태로 대기 금액을 유지한다. 이 버튼은 실제 송금을 요청하지 않는다. 성공 또는 확정 실패를 기록할 때 신청 당시 대상과 모의 거래 참조를 대조한다. 성공은 금액·한국 시간 지급 일시도 입력한다. 같은 거래 증빙은 다른 신청에 재사용할 수 없다. 결과를 모르는 동안 취소·반려로 예약을 풀지 않는다.

정책 배분율·공제율은 기본 비활성·0이며 관리자가 TEST 비율을 명시해야 한다. 실제 계약 배분율이나 개인·사업자·법인의 세율을 임의 지정하지 않는다. 계좌 입력 대신 `TEST-` 참조로 합성 지급 대상을 준비한다. 실제 계좌번호·주민등록번호·신분증·파일·외부 URL을 새 지급 증빙 경로로 받지 않는다.

## 수익의 근거와 금액 보존

- 회원의 **10,000원 → 10,000P** 충전 기준과 회차별 서버 가격(기본100P)을 유지한다. 수익은 포인트 숫자 자체가 아니라 OP05에서 실제 소비에 배분한 원화 금액을 사용한다.
- TOPUP 소비 allocation과 구매 당시 author_id/work_id를 기준으로 원금·배분액·공제·순액·정책 버전을 한 번만 확정한다. 충전 수납 총액과 회차 소비를 이중 합산하지 않는다.
- 선물·이전 TEST 잔액·내부 광고 완료·무료 캠페인·구형 수익/정산 기록은 자동 수익이 아니다. 실제 광고사 확정 매출 연결은 별도 인수 대상이다.
- 이후 감액은 원분개에 연결한 불변 기록으로 남긴다. 이미 지급한 결과를 지우지 않고 부족액과 추가 신청 제한으로 표현한다. 미사용 포인트 환불은 기존 소비 수익을 다시 감액하지 않는다.
- 신청·승인·발송 직전 최신 원거래, 지급 대상 버전과 작가 상태를 검사한다. UNKNOWN 이후 이미 실행한 결과는 당시 동결 대상과 맞는 증빙으로 기록하며, 이후 계좌 변경이나 정지가 재송금의 근거가 되지 않는다.

## 서버·권한·개인정보

`/api/v2/creator/payouts-test`와 `/api/v2/admin/payouts-test`를 기존 account gateway에 추가했다. 서버 검증 Auth UUID와 현재 작가 프로필, 최고 관리자 권한을 API와 DB에서 재검증한다. Author/Creator 명칭·경로·기존 권한 계약은 유지한다.

공개 capability는 `settlementsTestEnabled` 하나다. 기존 points TEST 게이트에 `SETTLEMENTS_TEST_ENABLED=true`, `SETTLEMENTS_TEST_ENVIRONMENT=TEST`가 함께 필요하다. 정적 기본값은 false이고 LIVE·무료 베타·불완전 설정은 DB 호출 전에 차단한다. 카드/광고 서비스 계약 여부를 임의로 준비 완료로 바꾸지 않는다.

`022_author_payouts_test.sql`은 검토용 신규 마이그레이션이다. 같은 파일에서 새 private 테이블의 RLS와 명시적 ACL, service_role 전용 RPC EXECUTE를 설정한다. 기존 019~021 함수 본문·ACL·행을 보존한다. API는 제한된 UTF-8 JSON, 동일 Origin POST, 입력 허용 목록, 정수 금액, 요청/행 버전을 검사하고 결과를 DTO 허용 필드로 투영한다. 새 요청은 회원별 제한과 requestId 지문을 적용하며, 응답 유실·408·미확정 오류는 동일 요청으로 재확인한다.

새 화면은 native DOM textContent, label, 상태 알림, 키보드 초점, 최소44px 조작 영역과 가로 스크롤 표를 사용한다. 화면 이탈·계정 변경은 늦은 응답의 표시를 차단한다. 같은 계정의 화면 이동에서는 미확인 요청을 유지하고 로그아웃에서는 폐기한다.

[R13 개인정보·국외 처리 조건](ui-r13-settlement-registration-2026-11-01.md)의 접수 게이트는 유지한다. 수동 서류 승인과 TEST 지급 대상 준비를 PASS·은행 예금주 확인·세무 완료로 승격하지 않는다. 이 단계에서 운영 DB 적용, 실제 계좌 검증, 송금, 세무 자료 수집 또는 금융 기능 활성화는 수행하지 않는다.

## 검증

합성 PostgreSQL에서 권한, 원장 보존, 근거별 수익 확정, 중복·초과 신청, 정책/계좌 변경, 승인과 지급 구분, UNKNOWN 예약 유지, 증빙 재사용, 감액·부족액을 검증한다. 실제 gateway와 합성 DB를 연결해 수익 확정부터 지급 증빙·후속 감액까지 왕복한다. API와 VM UI 검증, 기존 기능 회귀, 빌드·타입·번들·변경 보안 검사를 수행하고 결과는 최종 검증 집계에 기록한다.

브라우저·실기기, 실제 PostgreSQL 다중 연결 경쟁, hosted 복원, 실제 금융사 증빙은 이 합성 검증에 포함되지 않는다. 프로젝트에는 별도 lint 명령이 없으며 구문 검사와 변경 검토를 구분해 기록한다. VM UI와 SQL의 숫자 커버리지를 추정해 기재하지 않는다.
