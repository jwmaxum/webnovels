# OP-11 — 관리자 별도 송금 후 완료 기록

## 운영 방식

기본 지급 방식은 **관리자가 은행에서 별도 송금하고, 사이트에 결과를 기록하는 수동 지급**이다. 사이트의 ‘송금 대상 확정’ 또는 ‘송금 완료로 기록’ 버튼은 은행 이체를 실행하지 않는다. Toss 지급대행은 별도 계약과 인수를 마친 뒤 선택할 수 있는 자동 지급 경로다. 한 정산 신청에서 수동과 Toss를 동시에 사용할 수 없다.

이번 구현은 기존 `LOCAL_SIMULATED` 수익·정산 원장에 연결된 **TEST 절차**다. 수동 결과의 출처는 `MANUAL_ATTESTED_TEST`로 구분하며 기존 증빙을 실제 은행 증빙으로 바꾸지 않는다. 실제 송금·운영 DB 적용·금융 플래그 활성화는 하지 않는다. 실제 수동 지급에는 아래 OP-12의 실수익·실계좌·운영 조건 인수가 필요하다.

## 관리자·작가 UX

기존 ‘작가 정산 → 정산 신청 → 신청 상세’에서 처리하며 상위 메뉴를 늘리지 않는다.

1. 확정 수익을 바탕으로 신청을 승인한다. 승인만으로 지급 완료가 되지 않는다.
2. 기본 방식 ‘관리자 별도 송금’에서 대상·금액을 검토하고 **수동 송금 대상 확정**을 누른다. 실제 운영에서는 이 확정 뒤 은행에서 별도 송금한다. 현재 TEST에서는 모의 자료로만 검증한다.
3. 송금 결과를 확인한 뒤 **송금 완료로 기록**에 거래 참조, 증빙 보관 참조, 원래 지급 대상, 일치하는 금액, 한국 시간 송금 일시, 처리 사유와 대조 확인을 입력한다. 현재 참조에는 `TEST-` 접두가 필요하다. 실계좌·개인정보·은행 서류를 입력하지 않는다.
4. 결과가 불명확하면 **대사 필요 메모**를 남긴다. 예약금은 유지된다. 실패가 확인된 경우에만 증빙을 갖춰 **미송금 확정으로 종료**한다. 시간 경과·메모 작성만으로 예약을 해제하거나 재송금하지 않는다.
5. 작가는 본인의 지급 경로·금액·처리 결과·시각을 확인한다. 관리자 메모, 은행 거래/문서 참조는 작가 응답에서 제외한다. 다른 작가의 신청은 조회할 수 없다.

증빙 보관 참조는 운영자가 별도 보관한 모의 문서를 가리키는 식별자이며 파일 업로드나 은행 검증을 대신하지 않는다. 관리자 확인 기록과 은행 API 검증 결과를 구분한다. 대사 메모는 메모 자체로 지급 방식이나 원장 상태를 바꾸지 않는다.

완료 후 상위 상세·합계도 다시 조회한다. 타임아웃 시 같은 requestId·입력으로 확인하며, 새 처리 버튼을 잠가 중복 기록을 막는다. 페이지 이동 뒤에도 미확인 요청 대상을 표시한다. 로그아웃/계정 변경 시 보류 요청·입력과 늦게 도착한 응답을 폐기한다.

## Toss 지원 범위와 연결 조건

Toss 지급대행은 등록 셀러 계좌로 지급하는 API를 지원한다. 카드결제 PG와 별도 신청·심사·계약이 필요하며, 웹소설·웹툰 작가의 인세 지급이 해당 계약에 포함되는지는 Toss와 확인해야 한다. 임의 은행 계좌의 잔액을 출금하는 범용 송금 API가 아니며 지급 재원·가상계좌·지급 가능액 등 제공자 조건을 따른다. 이용료는 실제 계약으로 확인하고 코드에 고정하지 않는다. [서비스 신청](https://www.tosspayments.com/blog/articles/30355?from=category), [지급 기본 정책](https://www.tosspayments.com/blog/articles/30365?from=recommended)

- 개인·개인사업자·법인 셀러 유형과 본인확인/KYC 상태를 제공자 규격으로 검증해야 한다. 인증 필요 상태에서 자동 지급을 허용하지 않는다. 실제 인수 전 자체 금액 조건만으로 지급 가능 여부를 추정하지 않는다. [지급대행 가이드](https://docs.tosspayments.com/guides/v2/payouts)
- TEST에서는 법인 셀러 등 환경 제약이 있으며 TEST 계좌 확인은 실제 예금주 확인 증거가 아니다. 개인 작가의 실제 지급 인수를 TEST 법인 응답으로 대신하지 않는다. [TEST 환경](https://docs.tosspayments.com/guides/v2/get-started/environment)
- 요청 접수나 서명 웹훅 수신만으로 송금 완료하지 않는다. 원요청과 대조한 개별 조회의 `COMPLETED`가 자동 지급 완료의 근거다. UNKNOWN/FAILED/REVIEW는 자동 수동 전환의 근거가 아니다. [지급 상태·조회](https://docs.tosspayments.com/reference/additional)

현재 OP-10의 전용 TEST 설정·JWE 요청·웹훅/조회 대사를 재사용한다. OP-11 상세에는 그 제공자 상태와 최근 조회 시각을 표시한다. 외부 TEST 완료는 기존 모의 금융 원장의 PAID로 자동 변환하지 않으며 `ledgerApplied:false`로 명시한다. **실제 Toss 자동 송금·실수익 원장 자동 완료는 계약/키와 실거래 인수 전 미활성**이다. 수동 경로는 Toss 계약을 필수로 요구하지 않는다.

## 데이터·동시성 계약

`database/launch/024_manual_payout_workflow.sql`은 OP-07/10 뒤에 적용하는 검토 게이트가 있는 마이그레이션이다. 신규 private 테이블은 다음 5개다.

| 테이블 | 목적 |
| --- | --- |
| `commerce.op11_cases` | 신청별 한 가지 지급 경로 고정: MANUAL / TOSS_TEST / LEGACY_REVIEW |
| `commerce.op11_proofs` | 신청당 한 번의 수동 성공/실패 증빙, 전역 고유 거래 참조 |
| `commerce.op11_events` | 대상 확정·기존 미확인 건 인수·완료·실패·대사·메모의 불변 이력 |
| `commerce.op11_receipts` | 현재 관리자별 requestId + 입력 지문 멱등 결과 |
| `commerce.op11_limits` | 관리자별 분당 30회 신규 쓰기 제한 |

모든 테이블에 RLS와 명시 ACL 거절을 적용한다. `anon`/`authenticated`/`service_role` 직접 CRUD는 금지하며 서비스 전용 `public.op11_manual_payout`만 실행 가능하다. 현재 Auth와 최고 관리자/본인 작가 권한은 기존 검증 함수를 재사용한다. 작가 ID와 Auth UUID는 혼용하지 않는다.

수동 대상 확정·완료는 기존 원장 RPC를 같은 SQL 트랜잭션 안에서 사용한다. 관리자 쓰기 잠금 → 작가 잠금 → 원충전/지급 대상 → 신청 행 순서로 기존 잠금 계약을 따른다. 내부 RPC 오류가 나면 새 경로/증빙도 함께 되돌리고, 성공 시 기존 예약/기지급 계산을 그대로 사용한다. 금액·대상·시각 불일치와 재사용 거래 참조를 거절한다. 메모 한도에 도달해도 확인된 지급 결과 기록을 막지 않는다.

추가 트리거는 기존 OP-07 직접 시작/완료 호출도 경로·증빙 없이 통과하지 못하게 한다. OP-10의 원신청 share 잠금과 OP-11 수동 시작의 update 잠금으로 경로 선택 경쟁을 직렬화한다. Toss 경로 선택 후에는 원신청의 수동 시작·완료·반려·취소를 차단한다. 수동 확정 뒤에는 Toss 준비가 거절된다. 운영자가 은행에서 이체하는 행위 자체는 사이트가 제어할 수 없으므로 실제 운영에서는 송금 전 이 화면의 경로·상태를 확인해야 한다.

기존 OP-07/10 행과 함수 본문·ACL은 보존한다. 기존 외부 TEST 요청은 TOSS_TEST 경로로 연결한다. 이전 수동 UNKNOWN은 재전송 없이 ‘기존 미확인 건 인수’로 이어간다. 외부 요청과 수동 원장 이력이 충돌하면 LEGACY_REVIEW로 묶어 재발송/수동 전환을 차단한다. 이미 발송된 외부 요청의 조회는 계속 허용한다. 기록을 지우거나 READY로 초기화하지 않는다.

## API·적용 순서

- 관리자: `POST /api/v2/admin/payout-workflow` — detail, start, complete, failure, hold, note.
- 작가: `POST /api/v2/creator/payout-workflow` — 본인 detail만 허용.
- 환경: 기존 points/settlements TEST 조건에 더해 `MANUAL_PAYOUT_WORKFLOW_ENABLED=true`가 필요하다. 정적/public 설정 기본값은 false다. 다른 키나 금융 기능을 자동 활성화하지 않는다.
- 같은 origin, JSON, 최대 8KiB, 엄격한 필드·금액·UUID·시각 검증과 출력 투영을 적용한다. 현재 증빙 출처는 TEST만 허용한다.

적용 순서는 별도 합성/인수 DB에 019~024 의존 관계 확인 → 기존 이력 백업·충돌 확인 → 024 검토 적용 → 새 코드 배포 → 별도 검증 환경의 수동 workflow 게이트 활성화 → 역할·수동/Toss 경쟁·완료/실패/재시도·복원 인수다. 운영 적용과 플래그 변경은 이번에 수행하지 않는다. 024 적용 후 예전 클라이언트의 직접 begin/paid/fail은 차단되므로 새 코드와 게이트의 준비 상태를 함께 확인해야 한다.

되돌리기는 새 업무 진입을 비활성화하고 미확인 건을 보존하는 방식이다. 경로/증빙 트리거를 제거해 구형 우회 경로를 열거나 이전 DB로 덮어쓰지 않는다. 외부 발송 후 불명확한 건은 조회·대사하고, 실제 수동 송금은 확인된 은행 내역으로 처리한다.

## 검증과 후속 개발

`search-first`, `security-review`, `verification-loop`를 적용했다. 기존 jose/WebCrypto/Zod/SQL·TEST fixture를 재사용하며 추가 패키지는 없다. Codebase Memory가 Transport closed여서 소스 rg/read로 확인했다. 연구 에이전트가 Toss 공식 문서의 계약·셀러·TEST 조건을 조사했다. 추가 의존성이 없어 npm/PyPI 패키지 검색은 별도로 수행하지 않았고, 지급을 실행할 전용 MCP도 사용하지 않았다.

API·SQL·가상 DOM 검증, PostgreSQL 두 연결의 수동/Toss 경쟁·중복 완료·archive 복원 검증과 회귀/컴파일/보안 검사를 수행한다. 브라우저/localhost HTTP, 실제 은행 송금, 제공자 실호출, 운영 DB 적용은 범위에 포함하지 않는다. 검증 결과와 커밋·배포 결과는 별도 집계에 기록한다.

다음 **OP-12: 실수익 기반 수동 정산 운영 전환 준비**를 제안한다.

1. 실제 무통장 입금/PG 승인과 회차 소비의 실수익 출처를 TEST 원장과 분리하고 대조한다. 기존 모의 수익을 실제 지급 잔액으로 승격하지 않는다.
2. 승인된 작가 정산 등록의 계좌 revision·실수령인·정산 기간·수익/공제 명세를 지급 요청에 고정하고, 비공개 은행 증빙 보관·접근·보존 정책을 연결한다. 수동 실제 지급 출처는 별도 `MANUAL_EXTERNAL` 계약으로 정의한다.
3. 운영자 확인 후 실제 수동 송금 완료 기록·작가 조회·수정 불가 이력·오입력 정정 분개를 인수한다. 담당자 조회/승인/완료 권한 분리와 대사 예외 목록을 추가한다.
4. Toss 계약이 준비되면 작가 유형별 셀러 등록/본인확인·지급 가능액·원요청/조회/웹훅 인수 후 선택적 자동 지급을 연동한다. 제공자 상태와 실수익 원장 완료를 같은 검증된 거래에만 연결한다.
5. 암호화 master key의 구키 읽기/신키 쓰기·재암호화와 별도 hosted 복원·SMTP 인수는 후속 보안/운영 작업으로 이어간다. 수동 지급 기본 정책은 유지한다.

## 로컬 검증 결과

- 관련 회귀 54개 파일·644개 테스트 중 최초 643개 통과. 새 공개 설정 항목에 맞춰 기존 allowlist 테스트를 수정한 뒤 해당 파일 8개 모두 통과했다. 잔여 실패는 없다. OP-11 신규 20개 테스트도 통과했다.
- PostgreSQL 17.11 두 연결에서 수동/Toss 상호 배제, 동일/서로 다른 완료 요청 경쟁, archive 복원 후 경로·증빙·역할 보존 4개 시나리오를 통과했다. 합성 로컬 DB 결과이며 hosted 복원 인수는 아니다.
- 컴파일, TypeScript, Cloudflare Functions 6개 번들, 변경 JS 구문·보안·diff 검사를 통과했다. npm audit 취약점 0건. 별도 lint 설정은 없으며 coverage와 로컬 전체 release 연속 실행은 수행하지 않았다.
- 상세 집계: `artifacts/op11-verification-2026-11-02.json`. 운영 DB·플래그·실제 송금·제공자 실호출·브라우저 인수는 수행하지 않았다.
