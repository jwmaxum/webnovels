# UI-R9 — 운영 발행 왕복·휴대폰 인수

2026-10-31. 상태: **구현·릴리스 검증·운영 발행 왕복·029 운영 적용 완료**. 남은 수동 접근성·상세 Word 인수와 반복 성능 계측은 UI-R10에서 이어간다.

웹소설·웹툰의 새 회차는 작가가 직접 즉시·예약 발행한다. 이미 공개한 회차의 변경과 공개 이력이 있는 작품의 공개 중단은 기존 관리자 검토를 거친다. R9는 이 계약의 실제 운영 왕복을 확인하고 Word 붙여넣기·서식 도구·발행 안내를 보완한다.

## 실제 운영 인수 범위

사용자가 별도 무료 시험 작품의 즉시·예약 공개, 해당 자료만의 수정 승인과 공개 중단 승인, 종료 후 비공개 전환을 허용했다. 작가 계정과 별도 관리자 계정을 사용한다. 기존 작품·계정·권한은 변경하지 않는다.

| 자료 | 처리 범위·상태 |
| --- | --- |
| 작품 32 `조선 로맨스` | 기존 실제 연재 작품. 보존 대상이며 시험 수정·승인 대상이 아니다. |
| 기존 비공개 작품 33·34·35 | 기존 사용자 자료. R9 운영 왕복에서 변경하지 않았다. 작품 35가 휴대폰 인수 자료인지 추정하지 않는다. |
| 작품 36 `UI-R9 웹소설 기능 인수용` | 1화 작가 즉시 공개. 2화 **14:38 KST** 예약 → **14:38:52 KST** 자동 공개. 1화 수정 요청 후 기존 독자 공개본 유지, 별도 관리자 **14:47:49 KST** 승인과 독자 변경본 확인. **15:05:57 KST** 공개 중단 승인 후 비공개. |

예정된 검증 순서는 새 회차 즉시 공개 → 예약 시각 도래 후 기존 Cron의 공개 → 공개본 수정 요청 → 승인 전 독자 공개본 유지 → 별도 관리자 승인 → 독자 변경본 확인 → 공개 중단 요청·승인 → 독자 탐색·열람 종료다. 예약 완료 전에 작품 전체의 변경 기준을 잡는 수정 검토를 요청하지 않는다. 스케줄러 RPC를 수동 호출해 시각 도래를 대신하지 않는다.

소설·웹툰 모두 PENDING/RUNNING 예약은 0건이며, 비공개 전환 후 비인증 공개 작품 API는 `WORK_NOT_FOUND`를 반환했다. 공개 버전·원고·파일·승인 이력은 보존했다. 운영 DB 읽기 점검에서 기존 작품 32의 완결·공개 10화·공개 head 10개와 기존 비공개 작품을 확인했다. 네 건의 수정·공개 중단 승인 모두 요청 작가와 결정 관리자가 별도 신원임을 확인했다.

즉시·예약 발행과 수정 승인까지 브라우저 UI로 수행했다. 이후 확인창 응답 지연으로 브라우저 제어가 중단되어, 공개 중단의 최종 처리는 기존 작가·관리자 일반 인증 API로 완료했다. 직접 SQL로 검토를 우회하지 않았다. 중복 결함으로 잘못 반환된 다른 작품의 요청은 승인하지 않았고, 작품 37은 현재 제목을 그대로 포함한 동일 공개 중단 요청으로 구분해 정리했다. 이 임시 정리와 029의 근본 수정은 구분한다. API 전용 세션은 각각 로컬 범위로 로그아웃했으며 사용자 브라우저 전체 세션을 취소하지 않았다.

이 UI 인수는 당시 배포된 R8 코드에서 기존 발행 계약을 확인한 기록이다. R9 신규 서식 도구·접수 링크의 VM/DB 회귀 검증과 최종 배포 자산 확인을 실제 브라우저 신규 코드 인수로 확대하지 않는다.

### 029 운영 적용

현재 운영 논리 백업과 검증된 네이티브 덤프를 Git 밖에서 확인했다. 실제 백업의 행·기본값·시퀀스·앱 함수·트리거를 PGlite에 복원해 029를 두 번 적용했다. 원본 행, 기존 접수·결정, 함수 ACL, 공개 RPC, 전체 앱 제약과 컬럼 NOT NULL을 보존했으며, 허용한 변경은 작품별 UNIQUE와 비공개 `authoring.review_change`의 조회 두 곳이다. 역할별 `SET ROLE`로 브라우저·service_role의 비공개 함수 직접 실행 거절과 정상 서비스 RPC 접근을 확인했다.

로컬 PostgreSQL 18의 NOT NULL 제약 카탈로그 표현은 컬럼 `attnotnull`의 정확한 비교로 검증했다. 운영 제약·ACL 비교는 정규화하거나 완화하지 않았다. 최초 적용은 백업 후 행 변경을 감지해 원자적으로 중단됐으며, 최신 백업·리허설을 다시 수행한 뒤 029만 적용했다. 기존 마이그레이션 전체를 재실행하거나 기능 플래그·권한을 변경하지 않았다. 이 로컬 복원 검증은 별도 Supabase 프로젝트의 실제 복원 인수를 대신하지 않는다.

## 기기·클립보드·접근성의 확인 범위

- 사용자는 휴대폰 점검 질문에 **“갤럭시S26 chrome 브라우저에서 잘 진행됩니다.”**라고 응답했다. 실제 기기에서 전반적인 정상 동작을 사용자 보고로 기록한다. OS·Chrome 버전과 항목별 로그·측정값은 제공받지 않았으므로 별도 계측 또는 세부 항목별 합격으로 확대하지 않는다.
- Windows Microsoft Word의 별도 시험 문서에서 네이티브 복사를 시도했다. 브라우저 세션의 가상 클립보드 조회에는 데이터가 없었다. 이는 해당 조회 경로의 결과이며 모든 사용자의 Word 붙여넣기가 실패한다는 근거가 아니다. **실제 Word → 브라우저 클립보드 서식 보존은 아직 합격으로 기록하지 않는다.** 대표 Word HTML 변환·저장 검증과 구분한다.
- 사용자는 이후 **“PC에서 붙여넣기는 잘 되네요. My bad”**라고 정정했다. PC 붙여넣기 성공을 사용자 확인으로 기록하며, 저장·재로딩과 개별 Word 서식까지 항목별 인수를 마쳤다고 확대하지 않는다. 자동 브라우저의 대표 HTML 원고는 서버 저장·공개·독자 화면에서 굵게·기울임·밑줄·가운데/오른쪽 정렬과 줄바꿈을 확인했다.
- 200% 데스크톱 확대와 음성 스크린리더 낭독 인수는 미확인이다. DOM의 접근성 속성·VM 테스트를 실제 확대·음성 인수로 대신하지 않는다.
- 실제 LCP·CLS 반복 수집은 현재 자동 브라우저의 `PerformanceTimeline.enable` 미지원으로 완료하지 못했다. 운영 측정값·중앙값·개선율을 제시하지 않는다. 분석 도구의 합성 테스트만으로 운영 수치를 만들지 않는다. 이후 유효한 가시성 이력·동일 폭·캐시 조건을 확보한 제한된 반복 표본과 현장 Core Web Vitals·CrUX 백분위를 구분한다.

## Git·배포 기록

코드·검증 요약·이 문서를 단계 커밋에 포함해 `main`에 일반 push한다. 해당 커밋 ID와 GitHub CI·Cloudflare 배포·변경 자산 확인 결과는 최종 완료 보고에 기록한다. 검증 자료는 `artifacts/ui-r9-verification-2026-10-31.json`과 `artifacts/ui-r9-browser-2026-10-31.json`을 따른다. `.env.local`·자격 증명·DB 덤프·원시 사용자 자료는 커밋하지 않는다. Vercel은 사용하지 않는다.

## 다음 개발 — UI-R10과 외부 베타 인수

1. 미확인인 실제 Word 클립보드, 검증된 200% 확대, 음성 스크린리더 인수를 수행한다. 문제가 재현되면 사용 환경·발생 순서·기대 서식과 실제 결과를 기준으로 최소 범위를 수정한다.
2. 동일 조건의 홈·첫 회차 반복 측정에서 실제로 비용이 확인된 자원부터 개선한다. 제한된 실험값과 현장 이용 통계는 분리하고, 근거 없이 아이콘·서체 교체나 개선율을 약속하지 않는다.
3. 기존 37단계의 SMTP 확인·복구 메일 실제 수신, 운영과 분리된 Supabase·private Storage 복원, 실제 PostgreSQL 경쟁 요청·권한 회수 인수를 이어간다. SMTP·독립 복원 준비 전에는 외부 베타 전체 준비가 끝났다고 표시하지 않는다.
4. PASS·Toss 결제는 업체 계약과 관리자 키·채널 설정이 준비된 뒤 별도 운영 인수한다. 이번 무료 발행 확인을 본인 인증·결제·정산 인수로 확대하지 않는다.
5. 웹툰 참여자 입력의 `글 크레딧 / 그림 크레딧 / 원작 크레딧`을 `글 작가 / 그림 작가 / 원작 작가`처럼 이해하기 쉬운 명칭과 선택 입력 안내로 다듬는다. 한 사람의 겸임과 원작 없는 창작 웹툰을 구분하며, 표시 이름을 저작권·신원 인증의 근거로 사용하지 않는다.
