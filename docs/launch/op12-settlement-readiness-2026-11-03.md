# OP-12 — 수동 정산 운영 전환 준비

## 이번 단계의 결과와 운영 경계

관리자가 별도 은행 송금을 진행하고 완료를 기록하는 기본 정책을 유지한다. OP-12는 **계좌 확인·비공개 증빙·기간별 준비 기록**을 기존 작가 정산 메뉴에 추가한다. 작가는 본인의 준비 상태를 확인한다. 지급 승인·잔액 예약·은행 이체·지급 완료는 이 준비 기능의 동작이 아니다.

소스를 확인한 결과 현재 OP-04~11 결제·소비·정산은 `LOCAL_SIMULATED` 또는 별도 `PROVIDER_TEST`다. 기존 `public.author_earnings`의 기록상 `PAID`도 실제 입금·소비의 증거가 아니다. 따라서 OP-12는 실제 수익을 `0원`으로 꾸미거나 TEST 수익을 승격하지 않는다. `sourceStatus=UNCONNECTED`, 금액은 `null`, `canPay=false`로 고정하고 ‘연결 전’을 표시한다. 입력 JSON·환경변수로 이 제한을 해제하는 경로도 없다.

실수익 원천 수집 및 실제 지급 완료 원장은 **아직 연결되지 않았다**. OP-11 계획의 실제 거래→지급 연결과 실지급 정정 분개는 아래 OP-13 계약으로 이어간다. 이번 은행 증빙은 **계좌 확인용 자료**이며 송금 영수증·실제 지급 증거 접수 기능과 혼동하지 않는다. 현재 운영 DB, 기능 플래그, 기존 금융/계정/작품 자료를 변경하지 않는다.

## 화면과 권한

- 기존 관리자 ‘작가 정산’ 안에 ‘수동 정산 운영 준비’를 배치한다. 상위 메뉴를 추가하지 않는다. 필명/작가 ID 검색과 30명씩 페이지 이동, 상세 조회, 계좌 확인, 확인 철회, 증빙 열람, 대상 월별 준비 기록을 제공한다.
- 작가 ‘수익 내역’에는 본인 상태와 기간별 준비 기록만 표시한다. 무료 베타와 TEST 수익 화면에서도 준비 상태는 별도 영역으로 표시한다. 이미지·관리자 검토 목록·다른 작가의 자료는 반환하지 않는다.
- 신원 서류 `APPROVED`와 수동 계좌 확인을 분리한다. 기존 계좌 테이블의 `verification_status=PENDING` 의미와 암호화 형식을 바꾸지 않는다. 수동 확인은 금융기관 예금주 인증·PASS 인증이 아니다.
- 현재 활성 최고 관리자만 관리한다. 본인 계좌의 확인은 다른 최고 관리자가 해야 한다. 이는 승인된 운영자 역할을 확장하지 않는 최소 권한 경계다. 실제 지급 조회/승인/완료의 담당자 권한 분리는 OP-13 과제다.
- 계좌 확인·철회·증빙 열람은 현재 비밀번호 재확인과 현재 Auth를 요구한다. 추가 인증이 있는 계정은 기존 재인증 계약에 따라 거절한다. 비밀번호를 보관하지 않으며 재확인용 세션은 `scope=local`로 폐기한다.
- 은행명·예금주·끝 4자리만 화면에 표시한다. 계좌번호 원문을 새로 복호화하거나 계좌를 변경하지 않는다. 이 정보와 별도 자료의 실제 대조 책임은 운영자에게 있으며 확인 버튼이 은행 검증을 수행하지 않는다.

## 계좌·신원 변경과 증빙

확인 기록은 작가 ID, 소유 Auth UUID, 계좌 revision, 신원 신청 revision, 계좌 암호문을 포함한 현재 정보 지문에 묶인다. 계좌 변경·삭제·소유자 변경·신원 만료/철회·확인 철회·증빙 만료 시 현재 계좌 확인 상태가 무효가 된다. 기존 확인 기록을 수정하거나 삭제해 맞추지 않는다. 준비 기록은 생성 당시 상태를 보존하고 현재 상태와 다르면 재검토 필요로 표시한다.

새 비공개 증빙은 기존 AES-GCM과 전용 정산 키를 재사용하되 AAD 목적을 `bank-review:<documentId>:<identityRevision>`으로 분리한다. 소유자·작가·계좌 revision도 결속한다. 이미지 바이트 SHA-256을 대조하며 파일명·원문·비밀번호를 로그/응답에 남기지 않는다. JPEG/PNG 실제 형식·메타데이터·치수·150KB 제한은 기존 이미지 검증기를 재사용한다. UI는 번호와 불필요한 정보가 이미 가려진 이미지만 요구하며 자동 가림을 주장하지 않는다.

증빙 원문은 재인증한 최고 관리자에게만 반환하고 열람을 감사 기록에 남긴다. 화면 전환·로그아웃·계정 변경 시 입력과 미리보기를 지우고 Blob URL을 폐기한다. 증빙 미리보기는 60초 후 닫힌다. 늦은 응답은 다른 계정이나 화면에 반영하지 않는다.

증빙 보존 기간은 법정 기간을 추정해 고정하지 않는다. 아래 검토된 정책 설정이 없으면 접수를 거절한다. 기록에는 당시 정책 버전·해시·보존 일수·종료 시각을 고정한다. 종료 시각부터 열람·계좌 확인 효력은 차단하며, 서비스 전용 `op12_purge_documents()`가 100건씩 암호문을 파기한다. 원문 없는 확인·철회·감사·준비 메타데이터는 보존한다. 메타데이터의 최종 보존/정리와 법적 보존 예외는 운영 정책 확정 시 별도로 결정해야 한다.

## API·DB 계약

`database/launch/025_settlement_readiness.sql`은 009/016을 전제로 한다. `webnovels.settlement_readiness_apply_verified=true`라는 검토 게이트를 요구하고 재실행을 거절한다. 기존 함수 본문·테이블·계좌 키·금융 원장을 교체하지 않는다.

| 비공개 테이블 | 목적 |
| --- | --- |
| `launch_recovery.op12_documents` | 암호화된 계좌 확인 증빙·정책·만료/파기 시각 |
| `op12_reviews` | 계좌/신원/소유자 버전에 결속된 독립 관리자 확인 |
| `op12_revocations` | 원확인을 보존하는 철회 사유 코드 |
| `op12_snapshots` | 대상 월과 생성 당시 준비 상태, 금액 없는 기록 |
| `op12_audit` | 확인·철회·열람·준비 기록·파기 감사 |
| `op12_receipts` | 관리자별 requestId·입력 지문에 대한 멱등 결과 |
| `op12_limits` | 관리자별 신규 쓰기 분당 30회 제한 |

모든 테이블에 RLS와 명시적 직접 CRUD 거절을 설정한다. `anon`, `authenticated`, `service_role` 직접 접근은 금지한다. 고정 `search_path`의 서비스 전용 RPC만 실행 권한을 갖는다. 기존 Auth/소유권 확인을 재사용하고 계좌 등록과 같은 가상 계정→작가→계좌→신원 행 잠금 순서를 따른다. 캐시된 요청 결과를 돌려주기 전에도 현재 계정·권한을 확인한다.

- `POST /api/v2/admin/settlement-readiness`: list, detail, confirm, revoke, snapshot, reveal.
- `POST /api/v2/creator/settlement-readiness`: 본인 detail만 허용; authorId 입력 거절.
- 같은 origin·JSON·220KB 본문 한도·엄격한 입력 스키마·명시적 응답 투영을 적용한다. 관리자 검색은 요청 본문으로만 보낸다. 공개 설정에는 활성 여부 boolean만 노출한다.
- confirm/revoke/snapshot은 UUID requestId와 현재 지문을 사용한다. 네트워크 응답이 불명확하면 같은 요청으로 확인한다. confirm 요청의 무작위 암호문은 멱등 지문에서 제외하고 서버 HMAC·이미지 digest·정책·대상 정보를 비교한다.
- confirm이 성공해도 지급 승인이나 실제 정산 잔액은 생성하지 않는다. 실수익 수집·입금 확인·포인트 지급·송금 RPC를 호출하지 않는다.

## 운영 설정과 적용 순서

| 설정 | 조건 |
| --- | --- |
| `SETTLEMENT_READINESS_ENABLED` | 기본 false. 기존 정산 등록 키/기능 준비도 필요 |
| `BANK_PROOF_PRIVACY_REVIEWED` | 은행 증빙 처리 조건의 검토가 끝난 경우에만 true |
| `BANK_PROOF_POLICY_VERSION` | draft가 아닌 명시적 버전 |
| `BANK_PROOF_POLICY_TEXT` | 목적·항목·접근자·보존·파기·국외 처리 등 확정 안내, 200~8000자 |
| `BANK_PROOF_RETENTION_DAYS` | 검토된 1~3650일 정수. 범위 검증은 법률 적합성 판단이 아님 |
| `BANK_PROOF_CLEANUP_ENABLED` | 별도 scheduler에서 만료 원문 파기. 신규 접수가 닫혀도 독립 실행 |

기존 `AUTHOR_SETTLEMENT_*` 전용 키·개인정보 검토·최종 국외 이전 안내도 필요하다. 설정 존재 여부만으로 적법성을 보장하지 않는다. 비밀값을 채팅·Git·클라이언트에 넣지 않는다.

적용: 별도 합성/인수 DB에 025 적용과 ACL·변경 경쟁·복원 검증 → 운영 정책 확정 → 기존 자료 백업 및 변경 검토 → 운영 DB 승인 적용 → 새 Pages 코드와 별도 scheduler 준비 → 파기 기능 검증 → 준비 화면/증빙 접수 활성화 순서다. OP-12에서 운영 DB와 scheduler 배포/설정을 변경하지 않는다. 기존 무료 서비스는 유지한다.

접수를 중단해도 만료 파기 작업을 유지한다. 이미 저장한 증빙은 만료 접근 차단이 동작하므로 화면 기능을 끄는 것으로 보존 의무를 대신하지 않는다. 인수 전 실제 증빙을 시험 용도로 업로드하지 않는다.

## 조사·검증 범위

`search-first` → 구현 → `security-review` → `verification-loop`를 적용했다. 연구 에이전트가 공식 제공자 문서와 기존 구현을 조사했다. Codebase Memory는 Transport closed로 사용할 수 없어 경로를 제한한 rg/소스 확인으로 대체했다. 새 패키지 없이 기존 Zod·WebCrypto·PGlite·pg와 재인증/이미지 검증을 재사용했다. npm/PyPI의 추가 패키지 비교와 지급 전용 MCP는 사용하지 않았다.

Toss의 TEST 승인은 실제 자금 이동과 다르므로 상태값만으로 LIVE 수익을 판정할 수 없다. 제공자 환경·키·원주문·취소/환불·소비 연결을 서버에서 확인해야 한다. [Toss 환경](https://docs.tosspayments.com/guides/v2/get-started/environment), [API 키](https://docs.tosspayments.com/reference/using-api/api-keys). 웹훅만으로 실제 수익을 확정하지 않고 조회·원거래를 대조하는 원칙을 유지한다. [공식 웹훅 문서](https://docs.tosspayments.com/reference/using-api/webhook-events).

로컬 검증은 합성 DB/API/가상 DOM과 네이티브 PostgreSQL을 대상으로 한다. 브라우저·localhost HTTP·실제 은행/제공자 호출·운영 DB 적용은 수행하지 않는다. 세율, 공제율, 법적 보존 기간은 이번 단계에서 임의로 정하지 않는다. 상세 검증과 원격 반영 결과는 완료 기록에 추가한다.

## OP-13 — 실제 무통장 입금·포인트 소비 원장 연결

다음 단계는 **PG 계약이 없어도 준비할 수 있는 무통장 입금 경로부터 실제 수익의 원천을 연결**하는 것이다.

1. TEST와 별개의 실제 주문·입금 대조·포인트 lot·회차 소비 원장을 만든다. 기본 10,000원→10,000P, 회원 1~2화 무료, 이후 기본 100P 및 관리자 가격 계약을 유지한다. 기존 TEST/legacy 행을 복사해 실제 충전으로 만들지 않는다.
2. 은행 거래 고유 참조·입금액·주문 귀속·독립 확인을 결속하고 중복 입금/부분 대조/입금 취소를 처리한다. 실제 결제 원천 없이 관리자 임의 입력 금액을 작가 수익으로 만들지 않는다. 카드 LIVE는 별도 계약·키·승인/취소 인수 후 연결한다.
3. 원충전 lot에서 소비된 금액과 작품 소유자·정산 기간·계약 버전·환불/차지백·공제를 추적하는 실제 수익 집계를 구현한다. 서버가 검증한 연결만 `BANK_RECONCILED` 또는 `PG_LIVE_VERIFIED` 출처로 수용한다. TEST/증정/광고 포인트는 유상 수익과 분리한다.
4. OP-12의 유효한 계좌 확인을 실제 지급 신청에 고정한다. 실제 이체 증빙에는 `MANUAL_EXTERNAL` 목적과 별도 정책을 적용하고 조회/승인/송금 확인 권한, 지급 후 환불·오입력의 정정 분개를 추가한다. 완료를 READY로 되돌려 재송금하지 않는다.
5. 실제 수동 송금 인수 후 운영 전환한다. Toss 자동 지급은 별도 지급대행 계약·셀러/계좌 검증·가용 재원·원요청과 완료 조회 일치까지 확인된 경우에만 선택적으로 연결한다. 키 회전·hosted 복원·SMTP 인수는 별도 운영 과제로 유지한다.

## 로컬 검증 결과

- 관련 회귀 63개 파일, 712개 테스트 통과·실패 0건. OP-12 신규 테스트 14개를 포함한다.

- 상세 집계: `artifacts/op12-verification-2026-11-03.json`. 운영 DB/기능/scheduler 변경, 실제 증빙 업로드·송금·제공자 호출·브라우저 인수는 하지 않았다.
