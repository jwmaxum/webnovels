# 4단계 — 작가 작품 관리 계약·검증 기록

2026-09-23. **로컬 구현·검증 완료, 실제 Supabase·브라우저 통합 검증 대기**. 2단계 스키마/백업, 3단계 실제 이메일·Auth 매핑 검증은 완료되지 않았다. 운영 DB 변경·배포를 수행하지 않았다.

## 구현한 사용자 흐름

- 작가 센터 `내 작품`은 인증된 서버 사용자에 연결된 author_id로만 조회한다. 필명·대표작 제목·전체 `SAMPLE_WORKS`를 이용하던 작품 소유자 추정을 제거했다.
- 상단 `새 작품` 및 빈 목록 `첫 작품 등록하기`는 `/creator/works/new`의 독립된 작가 폼을 연다. 관리자 모달·작가 이름 입력·관리자 등록 핸들러를 호출하지 않는다.
- 제목 하나로 `DRAFT`/`PRIVATE` 작품을 생성한다. 작성자·필명 스냅샷은 DB의 현재 작가 프로필을 사용한다. 추천 플래그는 false다. 제목이 같더라도 요청 키가 다르면 다른 작품이다.
- 작품 상세 `/creator/works/:id`에 회차 목록, `/settings`에 작품 설정, `/reactions`에 독자 반응 진입점을 제공한다. 회차 목록은 메타데이터만 가져오며 원고 본문을 내려받지 않는다.
- 작품명·소개·장르·태그·이용등급·AI 사용·연재 상태를 설정한다. 장르와 태그는 관리자 필드와 분리된 쉼표 입력이다. 초안은 제목 외 항목이 비어도 저장되며 공개 전 누락 항목을 별도로 표시한다.
- 기본값 ALL/NONE이 사용자 선택을 뜻하지 않도록 `rating_confirmed`, `ai_confirmed`를 기록한다. 공개를 위한 소개·장르·등급·AI 표기 준비 여부는 게시 승인이나 공개 완료가 아니다.
- 표지가 없는 작품에는 해당 제목으로 기본 표지를 표시한다. 파일 업로드(6단계), 원고 작성/자동저장(5단계), 미리보기·게시(7단계), 독자 반응 관리(8단계)는 후속 구현이다. 이번 단계에서 성공한 것처럼 표시하지 않는다.
- 전체/비공개·초안/공개/휴지통 필터, 50개 단위 커서 조회, 로딩/정상 0건/조회 실패/재시도를 구분한다. 같은 필명·제목이어도 ID로만 상세·수정을 연결한다.
- 작가 작품 목록에서 관리자 연결과 근거 없는 정산 추산을 제거했다. 기존 관리자 메뉴는 9단계까지 남긴다. 기존 회차등록/수익/통계 등의 직접 DB 기능은 이번 단계의 완료 범위가 아니다.

## API 계약

모든 경로는 `/api/v2/creator/works` 아래이며 `P0_API_ENABLED=true`, P0 `locked`, `AUTHOR_WORKS_ENABLED=true`를 요구한다. 예제 설정의 기본값은 false다.

| 요청 | 내용 |
|---|---|
| `GET ?filter=all\|draft\|public\|trash&after=0` | 인증된 작가의 작품 최대 50개, `nextCursor`로 계속 조회 |
| `POST` + `Idempotency-Key: UUID` | `{title}`만 받아 비공개 생성; `{work, created}` 반환 |
| `GET /:id` | 소유한 작품과 회차 메타데이터 조회 |
| `PATCH /:id` | `version`과 허용된 설정 필드만 수정 |
| `POST /:id/trash` | `{version}`으로 휴지통 이동 |
| `POST /:id/restore` | `{version}`으로 비공개 복구 |

작품 ID·version·cursor는 문자열로 전달하여 JavaScript 정수 정밀도 손실을 피한다. 목록/상세/변경 모두 작가 프로필이 필요하며 최고관리자여도 author 프로필 없이 대신 작성하지 못한다. 본문·쿼리의 user_id/author_id/role을 권한으로 사용하지 않는다.

쓰기에는 정확한 same-origin Origin이 필요하다. 서버는 Auth 세션과 최신 프로필을 검사하고, DB RPC도 현재 작가 승인 상태·Auth 이메일 확인·차단 상태를 재확인한다. 서비스 전용 `public.creator_works` RPC는 고정된 허용 필드와 본인 작품 조건을 다시 검사한다. anon/authenticated가 직접 호출할 수 없다.

허용 설정은 `title`, `description`, `genre`, `tags`, `rating`, `ai_usage_type`, `serial_state`, `visibility`(PRIVATE만), `version`이다. 작성자·추천·정산·moderation·표지 URL·직접 공개 상태를 보낼 수 없다. 공개 작품의 등급 변경은 운영 검토 오류로 중단한다. 7단계 전에는 이 API로 PUBLIC을 설정할 수 없다.

서버가 반환한 version이 달라지면 409 `WORK_CONFLICT`로 중단한다. 화면은 실패한 입력을 보존하고 `최신 내용 불러오기 (입력 초기화)`를 별도 제공한다. 소유하지 않은 ID는 404, 제한 상태는 403, 설정/DB 장애는 503이다. 3단계 공통 오류 및 요청 ID 계약을 유지한다.

작품 관리 활성화 시 구형 작가용 `/api/v2/works/:id PATCH`는 새 경로로 안내하며 거절한다. 기존 작가 회차 PATCH는 5단계 편집 API 준비 전 중단한다. 관리자 기존 CONTENT_WRITE 경로까지 폐쇄한 것은 아니며 9·10단계에서 전환해야 한다.

## 재시도와 저장 안전성

등록 요청 키와 최초 제목은 계정 UUID별 sessionStorage에 보관한다. 응답이 유실되면 같은 탭을 새로고침해도 같은 키/제목으로 재시도하며, DB는 동일 작품을 반환한다. 같은 키로 제목이 달라지면 409다. 성공이 확인되어야 키를 제거하고 다음 작품을 새 요청으로 등록한다. 같은 제목을 중복으로 사용하는 것은 허용한다.

이 저장소는 비밀번호/토큰을 포함하지 않는다. 탭 종료·저장소 삭제·다른 기기에서는 미확인 요청 키를 복구할 수 없으므로 기존 목록을 먼저 확인해야 한다. 실제 저장된 작품은 서버 조회로 다른 기기에서도 접근 가능한 계약이지만, 실제 기기 간 시험은 미실행이다.

작가 행 잠금과 `(user_id, request_key)` 유일 키로 중복 생성을 막고, 작품 생성·관리 상태·요청 기록을 한 트랜잭션에 저장한다. 수정은 작품/상태 잠금과 version 비교로 덮어쓰기를 막는다. 네트워크 오류에는 자동 쓰기 재전송을 하지 않는다.

화면의 제목/소개/장르는 HTML로 실행되지 않도록 이스케이프한다. 새로 수정 가능한 메타데이터가 전달되는 기존 독자 카드·관리자 템플릿의 해당 문자열 출력도 보완했다. 전체 사이트 보안 검토를 대체하지 않는다. 로그인 사용자 변경/로그아웃 뒤 늦은 응답은 작가 화면을 다시 채우지 않으며, 같은 사용자 SIGNED_IN 알림은 열린 폼을 초기화하지 않는다.

## 공개·연재·휴지통·제재

| 작업 | 결과 |
|---|---|
| 휴재/완결 변경 | serial_state만 의미상 변경. 기존 공개 작품은 공개 유지, 비공개 작품은 비공개 유지 |
| 비공개 전환/휴지통 | 공개 작품의 호환 status를 DRAFT로 변경하여 공개 목록·읽기를 중단 |
| 대기 중 새 예약 | authoring.schedules를 CANCELLED로 변경 |
| 실행 중 새 예약 | `SCHEDULE_RUNNING` 409로 전체 변경 중단 |
| 구형 회차 예약 | SCHEDULED 또는 DRAFT/PUBLISHED의 미래 scheduled_at을 취소하고 회차 DRAFT로 전환. 이전 상태·시각을 private 취소 기록에 보존 |
| 복구 | PRIVATE 유지, 예약 자동 복원 없음. 연재 상태와 제재 상태 유지 |
| 원고·파일 | 작품/회차/초안/revision/공개본/파일 참조를 물리 삭제하지 않음. 예약 취소에 필요한 회차 상태·시각만 변경 |

제재 상태·사유는 작가가 수정할 수 없다. 제한된 작품도 휴지통 이동/복구는 가능하지만 제한은 해제되지 않고 설정 수정은 거절된다. HIDDEN 등 기존 회차 제재 상태를 예약 취소 과정에서 DRAFT로 바꾸지 않는다. 파일 바이트 삭제나 보존 기간에 따른 purge는 구현하지 않았다.

## 적용과 복구

[005_creator_works.sql](../../database/authoring/005_creator_works.sql)을 004 이후, `webnovels.authoring_apply_verified=true` 검토 게이트를 거쳐 적용한다. 실제 필수 열·ID 기본값·상태 enum·장르/태그 배열·Auth 매핑을 대조하고 복원 가능한 백업을 먼저 확인한다. 여기서 운영 DB에 적용하지 않았다.

기존 작품 원본을 수정하지 않고 authoring.work_state가 없는 행만 실제 author_id/status에 따라 초기화한다. 이미 존재하는 관리 상태와 공개 상태가 불일치하면 자동 덮어쓰기 대신 마이그레이션을 중단한다. 런타임에 소유 작품의 관리 상태가 누락되거나 공개 상태와 어긋나도 정상 빈 목록으로 처리하지 않는다. 알 수 없는 기존 운영 상태는 제한 상태로 이관한다.

private 추가 테이블은 work_create_requests와 cancelled_episode_schedules이며, public에는 service_role 전용 RPC만 노출한다. 권한 확인 함수/조회 helper의 search_path는 비어 있다. .env.example과 CI만 변경했으며 실제 환경 변수는 수정하지 않았다.

실환경 적용 전 **구형 예약 실행기를 중단**하고 기록을 검토한다. 7단계 예약기는 공개/제재/휴지통 상태를 확인하고 작품→상태→예약/회차 잠금 순서를 지켜야 한다. 9·10단계 전에는 관리자/다른 직접 DB 쓰기가 이 상태 모델을 우회할 수 있으므로 운영에서 혼용하지 않는다.

오류 시 AUTHOR_WORKS_ENABLED=false로 신규 경로를 제한하되 DB 데이터·멱등 기록·취소 기록을 삭제하지 않는다. 10단계 전체 API/RLS 전환 전 운영 활성화하지 않는다.

## 검증 기록

- `npm run test:creator-works`: API mock 4개, DOM 대역/VM 6개, 합성 PostgreSQL 7개. 실제 PostgreSQL 쿼리로 생성·재시도·소유권·수정 충돌·열 허용 목록·50개 페이징·enum·휴지통·복구·원고/파일 보존·예약 취소·제재 보존·RPC 권한을 검사했다.
- 기존 보안 API 26개, Auth 세션 VM 8개, Cloudflare 4개, 데이터 계약, `tsc --noEmit`, 변경 JS 구문·`git diff --check` 검증.
- SQL 시험은 합성 스키마에 P0 확장 및 authoring 001/003/004/005를 적용한다. 실제 Supabase schema dump·Storage 바이트·복수 프로세스 동시성 검증은 아니다.
- 프로젝트 규칙에 따라 localhost/브라우저 테스트를 시작하지 않았다. 화면 검증은 DOM 대역/렌더러 테스트이며 실제 브라우저 배치·키보드/모바일 사용성 시험은 대기다.
- [실행 증거](../../artifacts/step4-creator-works-verification.json). 1~3단계의 과거 검증 해시는 당시 소스 기준이므로 이번 변경 후 현재 소스 일치 증거로 사용하지 않는다.

다음 5단계는 작품 상세의 서버 ID를 받아 초안/revision 편집·자동저장·복구를 구현한다. 2·3단계 외부 의존성이 해결되기 전에는 4단계 통합 완료나 오픈 승인으로 기록하지 않는다.
