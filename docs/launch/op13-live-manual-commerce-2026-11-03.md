# OP-13 — 실제 무통장입금·포인트·작가 수익·수동 지급 원장

## 결과와 운영 경계

실제 운영용 수동 은행 거래 경로를 새 `live_commerce` 원장에 구현했다. 기존 OP-04~11의 TEST lot·열람권·수익과 legacy 잔액은 가져오지 않는다. 실제 은행 이체를 실행하는 코드는 없으며, 관리자가 은행에서 별도 처리하고 증빙과 고유 거래번호를 기록한다. `BANK_RECONCILED`는 **독립된 관리자의 은행자료 대조**를 뜻한다. 은행 API 인증이나 자동 입금 확인을 뜻하지 않는다.

이번 검증 자료는 모두 합성 자료다. 운영 DB 마이그레이션, 입금 안내·개인정보 정책 설정, 기능 활성화, 실제 입금·환불·작가 송금, 실제 증빙 접수, scheduler 배포는 수행하지 않는다. 기존 무료 연재를 유지한다. OP-12 준비 화면은 `UNCONNECTED/canPay=false` 계약을 그대로 유지하며, 새 실제 원장 화면과 혼동하지 않는다.

## 사용자 흐름

- 독자: `/wallet` 및 서재의 포인트 메뉴 → 10,000원/10,000P 주문 → 사이트의 확정 입금 안내에 따라 송금 → 관리자의 대조 완료 후 충전. 회원은 1~2화 무료, 이후 작품별 가격을 확인하고 구매한다. 기본 입력은 100P다. 웹소설 서식 본문과 웹툰 이미지는 구매 권한을 서버에서 다시 확인해 반환한다. 기존 `/read/:work/:episode`도 활성화 시 새 열람 화면으로 연결한다.
- 관리자: 기존 ‘작가 정산’ 메뉴 안에서 주문/회원 ID 검색, 입금 등록·증빙 확인·독립 확인, 작품 검색·가격/계약 버전 관리, 정산 신청 승인·공제 근거·외부 송금 완료, 환불/입금 취소 대사를 제공한다. 새 상위 메뉴를 추가하지 않는다. 목록은 30건씩 조회한다.
- 작가: ‘수익 내역’에서 본인 실제 원장의 신청 가능 수익과 신청/승인/지급 상태를 본다. 유효한 OP-12 계좌 확인이 있어야 신청할 수 있다. 다른 작가나 은행 증빙·관리자 ID를 반환하지 않는다.
- 환불 요청: 독자는 기존 문의 경로에 주문 ID를 남긴다. 문의 본문에는 계좌번호·신분증을 요구하지 않는다. 관리자가 외부 환불 후 미사용 잔액 전액의 환불 기록을 접수하고 다른 관리자가 대조한다. 일부 미사용 금액만 임의로 나누어 환불하는 기능은 포함하지 않는다.

## 원장 불변식

1. **원입금**: 주문에 입금 안내 버전 지문을 고정한다. 입금 등록 시 설정된 수취 계좌 식별자와 당시 안내 지문을 대조한다. 수취/출금 계좌 식별자+은행 거래번호의 서버 HMAC을 고유화한다. 한 주문의 충전은 한 번만 가능하다. 금액 불일치·부분/초과 입금은 기록 상태로 남고 충전하지 않는다. 서로 다른 부분 입금을 자동 합산하지 않는다.
2. **독립 대조**: 입금 기록자·확인자·충전 대상 회원을 분리한다. 최고 관리자만 처리하며, 민감한 쓰기와 증빙 열람은 현재 비밀번호 재확인 및 현재 Auth/DB 권한을 요구한다. 권한을 잃은 계정은 멱등 결과도 다시 받지 못한다.
3. **원충전 추적**: 확인된 입금 하나가 10,000P lot 하나를 만든다. 1P=1원으로 고정하고 증정·광고·TEST 포인트는 연결하지 않는다. 구매는 FIFO lot 배분·차감·열람권·작가 수익을 같은 트랜잭션에서 처리한다. 한 회차의 유효한 구매가 있으면 다시 차감하지 않는다.
4. **가격·발행 버전**: 5분 견적에 가격 정책과 공개 원고 버전을 고정한다. 가격 또는 공개 버전이 바뀌면 재확인한다. 작품 소유자 변경 시 기존 계약을 자동 승계하지 않는다. 작품/공개 head의 현재 상태도 다시 검증한다.
5. **수익**: 구매 당시 체결된 계약 참조·작가 Auth UUID·작가 ID·배분율을 고정한다. 수익은 구매 원화×계약 배분율(basis point)을 원 단위 내림한다. 특정 계약 배분율·세율을 임의로 기본 확정하지 않는다. 공제액과 계약·세무 검토 참조는 관리자가 지급 승인 때 입력한다. 외부 계약과 세무 검토의 사실 자체를 소프트웨어가 인증하지 않는다.
6. **지급**: 신청 시 현재 계좌/신원 지문과 OP-12 검토 ID, 원천 구매 목록, 신청 금액을 고정한다. 승인 후 별도 담당자가 은행 송금 증빙·실제 시각·정확한 순지급액을 기록한다. 수취 작가와 승인자·완료 기록자가 같을 수 없고 승인자와 완료 기록자도 달라야 한다. Toss 전송 경로는 없다.
7. **취소/정정**: 완료된 지급은 READY로 돌아가지 않는다. 미송금 신청 취소에는 은행 대조 확약과 근거 문서 참조를 요구하고 승인자가 직접 취소할 수 없다. 입금 취소 확인은 해당 lot에 연결된 구매를 회수하고 수익을 차감한다. 이미 지급했다면 작가 원장에 음수 잔액이 남고 추가 지급을 막는다. 여러 lot을 사용한 회차가 회수되면 취소되지 않은 lot의 사용분은 다시 사용 가능해진다.
8. **불명확한 응답**: UUID 요청 키와 입력 지문을 고정한다. 암호화 IV만 달라진 재시도는 같은 요청으로 처리하고, 다른 금액/대상/증빙 입력은 충돌로 거절한다. UI는 재시도 때 요청 키를 유지한다. 비밀번호는 저장하지 않고 재입력한다.

DB는 금융 처리를 하나의 advisory transaction lock으로 직렬화한다. 초기 운영의 정확성을 위한 보수적인 선택이며, 네트워크 호출은 잠금 밖에서 끝낸다. 대량 운영 성능 보장은 아니다. 사용자/작가/lot 단위 잠금으로의 확장은 동일한 동시성 불변식을 검증한 다음 진행한다.

## 권한·암호화·보존

`database/launch/026_live_manual_commerce.sql`은 025와 authoring-021, `webnovels.live_commerce_apply_verified=true`를 요구하며 재실행을 거절한다. 기존 테이블·공개 콘텐츠 함수·그 ACL을 교체하지 않는다. 새 스키마의 모든 테이블에 RLS 및 `anon/authenticated/service_role` 직접 CRUD 금지를 명시한다. 고정 search_path의 새 서비스 전용 RPC만 실행 권한을 부여한다. 금융 이력은 append-only이며 catalog의 현재 정책 포인터·호출 제한·만료 증빙 파기만 별도 수정 경로를 가진다.

- `POST /api/v2/live-commerce`: 독자 본인 주문·잔액·목록·견적·구매·본문·이미지.
- `POST /api/v2/admin/live-commerce`: 관리자 검색·정책·입금·정정·지급·증빙.
- `POST /api/v2/creator/live-commerce`: 작가 본인 조회·신청. `authorId` 입력으로 대상을 바꿀 수 없다.
- `op13_registered_episode`: 서비스만 호출하는 기존 HTTP 본문/웹툰 이미지 경로 보호 조회. 구매 기능을 꺼도 별도 보호 설정은 유지한다. 등록되지 않은 작품은 기존 경로를 사용한다. 조회 실패를 무료 허용으로 해석하지 않는다.
- `op13_purge_documents`: 서비스 전용 만료 증빙 파기. HTTP 관리 버튼으로 직접 공개하지 않는다.

이미지는 기존 실제 PNG/JPEG 형식 검증·150KB 제한을 재사용한다. 불필요한 개인정보가 가려진 파일을 요구하며 자동 가림을 주장하지 않는다. 이미지·은행 참조·계좌 내부 식별자를 전용 AES-GCM 키로 암호화하고 목적을 `finance:BANK_DEPOSIT/MANUAL_EXTERNAL/REFUND/BANK_REVERSAL:<documentId>`로 분리한다. 이미지 digest를 복호화 후 대조한다. 관리자 열람은 감사 기록에 남고 화면은 60초 후 닫힌다. 계정/화면 전환 시 비밀번호와 Blob URL을 지운다. 브라우저 저장소와 로그에 증빙을 넣지 않는다.

증빙에는 정책 버전·해시·보관 일수·만료 시각을 고정한다. 만료 후 열람/신규 대조를 거절하고 cron이 암호문을 파기한다. 거래 고유 참조 HMAC과 원문 없는 감사/금융 이력은 보존한다. 이 메타데이터 및 백업의 최종 보존·정리 기간은 운영 법무·세무 정책에서 따로 확정해야 한다. HMAC에 쓰는 키를 교체하면 참조 중복 판정에 영향을 주므로 무계획한 키 교체를 금지하고 후속 회전 절차를 따른다.

## 운영 적용 순서와 설정

| 설정 | 용도 |
| --- | --- |
| `LIVE_COMMERCE_GUARD_ENABLED` | 026 적용 후 먼저 활성화. 구매를 중단해도 기존 무료 URL 차단을 위해 계속 유지 |
| `LIVE_MANUAL_COMMERCE_ENABLED` | 새 주문·포인트·정산 API/UI, 기본 비활성 |
| `LIVE_COMMERCE_RELEASE_REVIEWED` | 계약·은행대조·세무·개인정보·복원·권한 인수 검토 완료 표시 |
| `LIVE_BANK_DESTINATION_ID` | 회사 수취 계좌의 고정 내부 식별자, 실제 계좌번호 대신 사용 |
| `LIVE_BANK_DEPOSIT_INSTRUCTIONS` | 검토한 은행/예금주/입금 안내 (20~2000자) |
| `LIVE_FINANCE_PRIVACY_REVIEWED` | 금융 증빙의 목적·항목·접근·보존·국외 처리 검토 |
| `LIVE_FINANCE_PROOF_POLICY_VERSION/TEXT` | draft가 아닌 정책 버전 및 200~8000자 확정 고지 |
| `LIVE_FINANCE_PROOF_RETENTION_DAYS` | 검토한 1~3650일 보관 기간; 범위 검증은 적법성 판단이 아님 |
| `LIVE_FINANCE_PROOF_CLEANUP_ENABLED` | 별도 scheduler 파기 작업. 신규 접수 중단과 독립 유지 |

기존 전용 정산 암호화 키와 개인정보·국외 이전 고지가 필요하다. `NEW_SERIALS_ENABLED/P0_API_ENABLED=true`, 무료 베타와 TEST 금융/이전 sandbox는 꺼져 있어야 새 모드가 열린다. 키·계좌·고지 원문은 공개 config에 넣지 않고 활성 여부만 반환한다. 카드 PG와 Toss 자동 지급은 별도 계약·LIVE 인수 후 연결한다.

적용 순서: 별도 DB의 026/전체 마이그레이션 복원·실제 역할 ACL 검증 → 정책/수취 계좌/계약/독립 관리자 확보 → 승인된 운영 백업 → 026 검토 적용 → 기존 본문 보호 설정 → 증빙 파기 워커 및 알림 점검 → 코드와 금융 기능 활성화 → 작품별 가격/계약 등록 → 제한된 실제 입금/환불/정산 인수 → 운영 범위 확대.

기존 공개 DB 함수를 동적으로 교체하는 초안은 자동 승인 검토에서 기존 접근 경로 영향 때문에 거절되어 적용하지 않았다. 대신 기존 RPC를 보존하고 새 서버 조회로 등록 작품의 기존 HTTP 경로를 보호한다. 운영 반영에는 위 보호 설정의 영속 유지와 기존 서비스 전용 RPC가 브라우저에 노출되지 않는지 확인하는 ACL 인수가 필요하다.

## 조사와 검증

공통 search-first/security-review/verification-loop를 적용했다. 연구 에이전트가 기존 TEST lot·FIFO·정산과 공식 문서를 조사했다. Codebase Memory는 Transport closed로 사용할 수 없어 한정된 소스 검색을 사용했다. 새 패키지 없이 Zod·WebCrypto·pg/PGlite와 기존 재인증·본문/이미지 검증을 재사용했다. npm/PyPI의 신규 패키지 비교나 은행/제공자 API 호출은 하지 않았다.

원장 직렬화와 고유 제약은 [PostgreSQL 명시적 잠금](https://www.postgresql.org/docs/17/explicit-locking.html), [트랜잭션 격리](https://www.postgresql.org/docs/17/transaction-iso.html)를 참고했다. 서비스 전용 권한은 [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)를 따른다. [Toss TEST/LIVE 구분](https://docs.tosspayments.com/guides/v2/get-started/environment)에 따라 TEST 승인 상태를 실제 자금 근거로 가져오지 않는다.

검증 결과와 commit/CI/배포 기록은 완료 시 추가한다. 합성 DB·가상 DOM·native PostgreSQL 결과는 운영 DB·은행 실거래·브라우저 인수와 구분한다. 브라우저/localhost HTTP 검증은 실행하지 않는다.

## 다음 OP-14 — 제한된 실제 운영 인수와 대사 강화

1. 운영 정책·원천징수/사업자 구분·계약 배분율·증빙 보존을 확정하고, 운영과 다른 hosted 복원 대상에서 026 전체 경로와 private 원문 복원을 인수한다.
2. 수취 계좌 안내·독립 관리자·입금/송금 근거를 준비한 뒤 승인된 제한 범위에서 실제 10,000원 입금→100P 소비→환불/작가 수익→외부 송금 완료를 대조한다. 코드/합성 성공을 실거래 성공으로 대신하지 않는다.
3. 입금 안내 변경 전 주문, 잘못 연결한 입금, 부분/초과 입금, 증빙 만료 상태의 보류 건을 관리하는 예외 대사 화면과 재증빙 절차를 강화한다. 미사용 부분 환불·정산 후 환불의 회수/차감 운영 정책도 확정한다.
4. 월별 마감·세무 자료 내보내기·지급 원천별 배분 명세, HMAC/암호화 키 회전 및 통지/SMTP를 구현한다. 동시 처리 성능은 원장 불변식 검증을 유지하며 개선한다.
5. Toss 카드 결제·자동 지급은 각각 계약 및 실제 제공자 환경이 준비된 경우 별도 인수한다. 기본 지급은 관리자의 외부 송금 후 완료 기록이다.
